## 4. 数据模型

### 4.0 组件库 vs 游戏内容（全篇总纲）

```text
┌─ 组件库 Library ── 用户的长期资产，自己维护、跨项目复用 ──────────┐
│  道路 · 建筑 · 消耗品 · 装备 · 怪物 · 职业 · 技能 · 背景           │
│  来源：系统预设（可"恢复默认"）  ＋  用户自建（能改能删能复制）    │
└───────────────────────────────────────────────────────────────────┘
        │ 这一局从库里挑出要用的
        ▼
┌─ 游戏内容 Content ── 这一局到底怎么玩 ───────────────────────────┐
│  · 启用的 消耗品 / 装备 / 怪物 / 职业 / 技能                       │
│        → 进奖励池候选、玩家背包 / 穿戴、开局 class_pool、技能栏    │
│  · 铺到地图上的 建筑 / 道路　＋　起终点标记                        │
│        → 出现在地图格上                                            │
└───────────────────────────────────────────────────────────────────┘
        │ 导出
        ▼
   .pmod（自包含：把用到的组件定义一起带走）
```

> **一句话：库是工具来源，内容是实际构建出的产物。**
> 用户自建的组件和系统预设**地位完全相同**，都躺在库里，都能改、能删、能复制、能反复用。
> 库不因某个项目而生（像笔刷库不因某张图而生），也不随某个项目而亡。

**公共字段**（**八大类全都有，一个不多一个不少**：怪物 / 道具 / 建筑 / 道路 / 职业 / 技能 / 背景 / **NPC**）：

| 字段 | 必需 | 说明 | 八大类是否一致 |
|---|---|---|---|
| `id` | ✓ | 全局唯一；地图节点用 `ref` 引用；**来源由它的形状决定**（§3.2） | ✓ 都有 |
| `name` | ✓ | 显示名，改名不影响引用、不影响来源判定 | ✓ 都有 |
| `icon` | ✓ | Emoji 或图标名 | ✓ 都有 |
| `desc` | | 描述文本 | ✓ 都有 |
| `tags` | | 标签数组，**三个用途共用同一个字段**：① 奖励池 / 怪物池的 `filter` 筛选（§4.8.5①）；② **通行能力**（§4.5.2）；③ 编辑器里的分组与搜索 | ✓ 都有 |

> **没有"来源"字段。** 预设还是自建，靠 §3.2 的 id 形状**当场判定**（查内置预设表）。
> 这样各类自动一致——怪物能自建，道具能自建，技能也能自建，判定方式完全相同。
> 用户自建的技能和自建的怪物，在库里的待遇没有任何区别。

#### 4.0.1 属性体系：两资源 + 四能力（共 6 个）

**属性一共 6 个，分两类——这两类的行为完全不同，不能混着处理：**

| 类别 | 属性 | 有"当前值" | 会被消耗 / 恢复 | 归零后果 | 用途 |
|---|---|---|---|---|---|
| **资源** | `hp` | ✓ | ✓ | 败北 | 生存 |
| | **`mp`** | ✓ | ✓ | 只是放不了"贵技能" | **技能成本**（§4.8.3）——**不是"法术专属"** |
| **能力** | `patk` | — | — | — | 物理攻击力（力值链 ①） |
| | `matk` | — | — | — | 法术攻击力 |
| | `pdef` | — | — | — | 物理防御 |
| | `mdef` | — | — | — | 法术防御 |

- **`mp` 是正式的第 6 个属性**。早期文档只列了 `hp/patk/matk/pdef/mdef`，却已经在用 `mp`（蓝瓶回蓝、地形扣蓝）——
  **不完整的 `mp` 体系是最不可取的情况**：要么没有，要么成套。现在成套：
  ① 玩家能分配点到 `mp`；② **有成本的技能**扣它；③ 有恢复道具（蓝瓶）；④ 地形 `cost` 能扣 `mp`。
- **`mp` 消耗完全由技能自己的 `cost` 决定**——跟"是不是法术"无关：一个技能 `cost: { mp: 3 }` 就花 3，
  `cost: {}` 就不花。**我们让保底对 `basic_attack` / `basic_magic` 的 `cost` 设为空，所以它免费**——
  这是**我们对预设模板的设计选择，不是引擎规则**：作者完全可以把某个法术 `cost` 设成 `mp`（它就会真花 mp），
  也可以把保底对的 `cost` 改成非空（那它就不再是"免费保底"）。**物法之别靠的是 `dim`，不靠谁耗蓝**。
- **"不会陷入死局"的保证来自"保底对 `cost` 为空"这个默认设定**：只要保底对免费，即使 `mp = 0` 也能放、也能打；
  若作者把保底对也设成要 `mp`，那保底本身也会受 `mp` 约束——这是作者的设计自由，**引擎不保证不死局**。
- **能力四项永远是"上限值"**，不会被消耗，只在力值链里当输入。
- 下文"五维"的旧叫法一律按 **6 属性**理解（`hp` / `mp` / `patk` / `matk` / `pdef` / `mdef`）。
- **背包不是第 7 个属性**：它不参与任何判定，是**职业上的一个容量数字**（`inventory_size`，§4.2.4）。
  说它"是角色属性"指的是"你这个角色能带多少东西"，和上面这 6 个被力值链消费的属性不是一回事。

#### 4.0.2 两边的属性从哪来（玩家 ≠ 怪物）

| 侧 | 属性来源 | 形态 | 为什么 |
|---|---|---|---|
| **玩家（主角）** | 职业 `base_stats` ＋ **自由点分配**（§4.2.1） | **确定值**，玩家自己分 | 自己的角色要可控、可规划 |
| **怪物** | `stats` **区间 → 登场时摇定**（§4.8.2） | **有波动**，小怪 / 精英靠区间拉开档 | 敌人要有意外性；同一个房间也可能遇到强一点 / 弱一点的 |

> 所以**不是**"双方都摇区间"，也**不是**"双方都用分配"。玩家精确、敌人随机——这是故意的。
> 玩家侧还会**随着战斗不断获得自由点**（`point_reward`，§4.8.8），角色是**长出来**的；怪物一登场就定型。

> **"本局是否启用"不是组件自己的属性**，而是**项目对它的使用状态**（`project.enabledIds`）。
> 同一个哥布林在 A 局启用、在 B 局不启用，库里的哥布林只有一份、不被改动。

**地图件 vs 非地图件：**

| | 地图件 | 非地图件 |
|---|---|---|
| 包含 | 道路、建筑 | 消耗品、装备、怪物、职业、**技能** |
| 是否占地图格 | 是 | 否 |
| 成为"内容"的条件 | **铺到地图格** | **显式启用** |
| 被谁消费 | 网格移动（可走图 = 已铺节点集合） | 建筑奖励池、玩家背包 / 穿戴、怪物房、开局 `class_pool`、**技能栏（学会的）** |

> 起点 / 终点标记是**画布内建工具**（每图各一个、无属性定义），不占组件库名额。

### 4.1 怪物 `monster`
- 属于**非地图件**：不占地图格，需被建筑（怪物房 `monster_pool` / 宝箱怪物 `mimic.monster`）抽出来才出现在游玩里；**未启用的怪物不会进入任何池**。
- `stats`: **6 个属性的区间** `hp / mp / patk / matk / pdef / mdef`，各为 `[min, max]`。
  怪物**用区间**（不是点数分配）：登场时用 `stat_dice` 把区间摇成一个具体值，本场固定（§4.8.2 第一步）。
  区间越宽，这只怪越"波动较大"。
- **小怪 / 精英靠区间拉开档，不靠新字段**——精英怪只是区间更高，再打个 `tags: [精英]`：

| 档 | `hp` | `patk` | `matk` | `pdef` | `mdef` | 标注 |
|---|---|---|---|---|---|---|
| **小怪** | `[6, 12]` | `[2, 4]` | `[0, 2]` | `[1, 2]` | `[1, 2]` | — |
| **精英** | `[24, 40]` | `[6, 10]` | `[4, 8]` | `[4, 6]` | `[4, 6]` | `tags: [精英]` |

  > 用 `tags` 而不是新开一个 `rank` 字段：怪物池可以直接 `filter: { tags: [精英] }` 做"精英房"，
  > **机制已经在那儿了，不用再加字段**（§4.8.5①）。
- 怪物**不按玩家那把尺子来设计**——它是另一套标定（§6.1.1 数值标定基准）。
- **`attack_weights`**（可选）：**这只怪会哪些技能、各占多重**——**键就是技能 id**，例 `{ basic_attack: 3, poison_bite: 1 }`。
  出手时掷 `pick_dice` 按权重随机挑一个（§4.8.3）——**这是逼玩家兼顾两维防御的关键**。
  省略 = 只用 `basic_attack`（内建基础技能，**与玩家的保底对无关**）。
- `atk_roll` / `def_roll` / `stat_dice`（可选）：**覆盖**前置配置里对应的骰子（§4.8.7）。
- `reward_pool`（可选）：打赢这只怪后的**战利品池**（§4.8.5①）。抽取算法默认用前置配置的 `loot`，可用 `pick` / `copies` 覆盖。
- **`effects`**（可选）：**命中玩家时施加的效果**，结构为 `add_stat` / `add_tag` / `remove_tag` **三种 `op`**（§4.8.10）。
  **怪物不会 `learn_skill` / `forget_skill`**——教 / 夺技能只发生在消耗品、技能、事件三处，怪物命中只改数值、挂状态，
  不做"技能转移"（避免破坏平衡）。
  例：`effects: [{ op: add_tag, tag: 中毒, duration: 3, per_turn: { hp: -1 } }]`——被它打中一次就中毒 3 回合。
  这就是"怪物会下毒"的落点，**不新增任何机制，只是把 `effects` 挂到怪物身上**。
- **`point_reward`**（可选）：打赢给玩家**几点自由属性点**（默认 0）——**玩家变强的主渠道**（§4.8.8）。
  小怪给 1、精英给 5，靠档位拉开，**不掷骰**。
- `desc`: 背景文本

### 4.2 主角：职业给起点，玩家做分配

#### 4.2.1 属性从哪来（三段式）

```text
职业.base_stats      →  初始属性（确定值，不摇）
职业.free_points     →  开局自由点数
战斗 / 开箱的产出     →  后续获得的自由点数（point_reward，§4.8.8）
──────────────────────────────────────────────────────────
玩家属性    = base_stats + 已分配的自由点
剩余自由点  = free_points + Σ point_reward − 已分配的点
```

| 段 | 来源 | 举例 |
|---|---|---|
| **初始属性** | 职业的 `base_stats` | 骑士 `hp 5 / patk 3 / pdef 2` |
| **开局自由点** | 职业的 `free_points` | 骑士 `25` 点 |
| **后续自由点** | 战斗 / 开箱产出的属性点 | 打赢哥布林王 `+3` 点 |

> **"开局给多少点"是职业设定，不是引擎硬规则。** 你可以建一个职业 `free_points: 300`——
> 那是你的设计自由，引擎不拦。**硬规则只管"怎么分"**（§4.2.2）。

#### 4.2.2 分配规则（这一层才是硬规则）

给多少点是职业的自由，**但"怎么分"是引擎写死的**：

| 规则 | 内容 |
|---|---|
| **折算** | **1 点 = 该属性 +1** |
| **可分配到** | 6 个属性的任意一个（`hp` / `mp` / `patk` / `matk` / `pdef` / `mdef`） |
| **时机** | **任意时刻**都能加（战斗外、战斗中都行），没有单独的"升级界面" |
| **洗点** | **不可以**。加进去就是加进去了 |
| **剩余自由点** | **保留**，什么时候想加再加（不过期、不会被没收） |

- **玩家属性不是摇出来的**，是 `base_stats` + 玩家一点一点分出来的**确定值**（§4.0.2）。
- 举例：骑士（`base_stats.hp = 5`、`free_points = 25`），玩家把 25 点分成 `hp +8` / `patk +12` / `pdef +5` →
  最终 `hp 13` / `patk 12` / `pdef 5` / `mp 0` / `matk 0` / `mdef 0`，剩余自由点 0。
- **`mp` 通常初始为 0**（除非职业的 `base_stats` 给了）：想放法术就得先把点分给 `mp`，或者靠装备补。
  **这是"物法之别"的第一道门槛**，也是分配策略的核心取舍之一。
- **剩余点保留**意味着"我现在不确定该加什么"是可以的——但**加错了不能退**，这是设计上的重量。
- **点数可一直留存**：留存 10 点去挑战 Boss 前一次性分配，是完全可行的玩法。

#### 4.2.3 职业 `class`：起点 + 放大器

```yaml
- id: knight
  name: 骑士
  icon: 🛡️
  base_stats: { hp: 5, mp: 0, patk: 3, matk: 0, pdef: 2, mdef: 0 }   # 初始属性（先天）
  free_points: 25                                                     # 开局自由点数（先天给你的本钱）
  buffs: { hp: 110, patk: 120, pdef: 110, matk: 80 }                  # 先天优劣（百分比，力值链 ③）
  inventory_size: 50                                                  # 背包格数（省略 = 50；0 = 无限）
  starting_items: [red_potion]                                        # 出生时口袋里有什么（可选）
  desc: 物理攻击较强的近战，生命与物防较高，法术攻击较弱。
  # 注意：没有 skills —— 职业不限定你能学什么（§4.8.3）
- id: mage
  name: 法师
  icon: 🧙
  base_stats: { hp: 3, mp: 4, patk: 0, matk: 3, pdef: 0, mdef: 2 }
  free_points: 25
  buffs: { hp: 90, matk: 130, mdef: 120, patk: 80 }                  # ← 这个 80 使他的物攻先天低于基准
  inventory_size: 30                                                  # 书多的人，可携带量少
  starting_items: [blue_potion, scroll_of_fireball]                   # 出生带一本《火球术》，但书可以丢弃可以出售
  desc: 法术攻击较强，生命值偏低，物理攻击较弱。
```

| 字段 | 作用 |
|---|---|
| **`base_stats`** | **初始属性**（6 个属性的确定值，不摇） |
| **`free_points`** | **开局自由点数**（想给多少给多少，300 也行） |
| `buffs` | 各维**百分比**（默认 100）——力值链第 ③ 环（§4.8.2） |
| `tags` | 通行能力标签（§4.5.2），如"水手"带 `tags: [渡河]` |
| `inventory_size` | **背包格数上限**（默认 `50`，`0` = **无限**）。它是**职业属性**，所以不同职业可以背得不一样多 |
| `starting_items` | **出生时背包里带的东西**（道具 id 列表，可选）。**它是"家当"，不是"本事"**——想给技能就塞一本技能书，但那仍然只是一件可丢弃可出售的道具 |

**职业 = 先天的属性配置。它只决定这几件事，多一件都没有：**

| 先天给什么 | 字段 | 后天呢 |
|---|---|---|
| **属性起点** | `base_stats` | 玩家用挣来的 `point_reward` 继续加（§4.2.1） |
| **优劣百分比** | `buffs` | **改不了**——这就是"带着先天减益成长"里那个 debuff |
| **背包容量** | `inventory_size` | 改不了 |
| 附带家当 | `starting_items` | 随时即可丢弃、出售、赠予 |
| ~~技能~~ | **没有 `skills`** | **全靠后天学**（技能书 / 事件 / 商店，§4.8.3） |

> **铁律：职业不限定技能。** 角色是**先天**的，但**长成什么样是玩家自己塑造的**。

- **"法师练成战士"是被允许的，而且取舍真实可见**：把点数全部分配给物攻、学到盾击、抢到铁剑——
  他确实能发动物理攻击了，**但永远承受 `patk: 80` 那个八折**。
- **先天改不了、后天自己选** —— 玩家的乐趣正是**用后天的选择去对抗先天获得的配置**。
- **职业与分配配合才成立**：法师把点数分配在 `matk`，百分比再放大 30%；
  要是分配在 `patk`，职业的 `patk: 80` 会把它**按 ×0.8 计算**——这就是分配该有的取舍。
- 职业**没有 `stats` 区间字段**：玩家属性 = `base_stats` + 分配，职业只负责起点与放大。
- `class_pool`（前置配置里的顶层列表）：控制开局**给玩家挑的出身卡片**；长度 1 = 只有这一种（直接选定），>1 = **玩家手选**；想要运气就由玩家自己点「掷骰决定出身」（**不在加载时静默随机**）。
- **装备无职业限制，技能也无职业限制**——任何职业都能用任何装备、学任何技能。

#### 4.2.4 背包 `inventory_size`（"能带几样东西"）

| 项 | 规则 |
|---|---|
| **字段** | `inventory_size`（整数，默认 `50`，**`0` = 无限**） |
| **挂在哪** | **职业**上（所以它是角色属性，是内容，不是前置配置） |
| **算格子还是算堆叠** | 按 **`{ id, count }` 条目数**算——**同一种道具算 1 格**（10 瓶红瓶占 1 格） |
| **超了怎么办** | 拾取时**直接拒绝并提示"背包已满"**（不做自动丢弃，避免误删） |
| **解除状态算不算占格** | 不算。状态挂在身上（§4.8.10），不占背包 |

- **默认 50 是"够用但会满"的量级**：想做成"仓鼠流"就给 `0`（无限），想做成"抉择流"就给 `30`——
  **这是设计者的一句话，引擎不干涉**。
- 编辑器在职业表单里就是一个数字输入框 + 一个"无限"勾选（勾上 = `0`）。

### 4.3 道具 `item`
统一分组，用 `kind` 区分：

**持续性 = 装备 `equipment`**
- `slots`: 占用的槽位，取自 `head / hands / feet / body / weapon`，可多槽
- `modifiers`: 对 **6 个属性**的加值 `{ hp, mp, patk, matk, pdef, mdef }`（任意整数，可正可负，不强制平衡）。
  **这就是力值链第 ② 环**（§4.8.2）——装备的作用是"加"，不是"乘"。
  **加值量级要按 §6.1.1 的基线标定**：普通件 `+1~2`，强力件 `+4~6`——一件装备顶掉 1/7 的点数预算才叫"强力"。
- **`tags`**：装备**最常用来当通行能力**（§4.5.2）——火抗鞋 `tags: [火抗]`、小船 `tags: [渡河]`。
  **"火焰山 + 火抗鞋"就是靠这个组合产生的**，编辑器不需要认识"火抗"这个词。
- **槽位冲突规则**：新装备若与已装备项在任一槽重叠，旧的那件**整体被卸下**
- 只能有 **5 个槽**，所以"带几把钥匙"是有取舍的：**穿火抗鞋就穿不了渡河靴**，这正是玩点。

**一次性 = 消耗品 `consumable`**
- `usable`: `[battle, move]` 子集，表示对战 / 前进时可用
- `effects`: **五种 `op`**，**可混在一个列表里**（完整定义见 §4.8.10）：

| `op` | 参数 | 作用 |
|---|---|---|
| `add_stat` | `target` / `stat` / `delta` | 即时改数值——可加/减 6 属性中任意一项的 `self` 或 `opponent` |
| `add_tag` | `tag` / `duration` / `per_turn?` / `modifiers?` | **挂状态**（中毒、御火符、力量祝福）——`duration` 必填、有硬上限 |
| `remove_tag` | `tag` | **解状态**（解药） |
| **`learn_skill`** | `skill` | **学会一个技能**——**技能书就是这个**（§4.8.3） |
| **`forget_skill`** | `skill` | **忘掉一个技能**——环境夺走你的本事 |

- **`tags`**（可选）：消耗品也能带标签。**`tags: [货币]` 只是给编辑器筛选用**（§4.8.11），引擎不认识这个词。

**技能书 = 一件普通消耗品** —— 「后天发育」的唯一载体（§4.8.3）：

```yaml
- id: scroll_of_fireball
  name: 火球术残卷
  icon: 📜
  kind: consumable
  usable: [move]                 # 走路时读，或者战斗前读
  effects:
    - op: learn_skill            # 读完，这招就跟着你了（永久）
      skill: fireball
  desc: 纸已经脆了，但字还认得。
- id: scroll_of_oblivion
  name: 遗忘之书
  icon: 🕳️
  kind: consumable
  usable: [move]
  effects:
    - op: forget_skill           # 反面：真的会把本事拿走
      skill: shield_bash
```

- **它是道具，所以开箱 / 事件 / 商店 / 战利品，凡能给道具的地方都能给技能**——**零新增通道**。
- **没有任何职业限制**：法师能读《盾击》，战士能读《治疗术》。
  > 编辑器在 `learn_skill` 行旁边显示被指技能的**说明预览**（"学会：用物攻攻击对手 `pdef`"），并校验它**已启用**。
  > 若玩家**已经会了**，游玩态直接提示"你已经掌握这招了"（书不消耗，避免浪费）。
- **恢复道具就是 `target: self` + `delta` 为正**，两种资源各有一瓶（量级同样按基线）：

| 道具 | `effects` | 在基线里的分量 |
|---|---|---|
| 红瓶 | `[{ target: self, stat: hp, delta: 5 }]` | 约 1/6 的初始点数预算 |
| 蓝瓶 | `[{ target: self, stat: mp, delta: 5 }]` | 同上；`mp` 默认是 0，所以蓝瓶往往比红瓶更"救急" |

- **消耗品现在能做"临时通行能力"了**：`add_tag` + `duration`（如"御火符 → `火抗` 3 回合"，§4.8.10）。
  但它**扛不起长期权限**（走 3 格就失效）；要当常备钥匙，还是做成占槽的装备
- **`mp` 恢复的唯一来源**在 MVP 里就是蓝瓶 + 分配点数：法术是有成本的（§4.8.3）

### 4.4 建筑 `building`
- 属于**地图件**：必须放到地图格才生效；可多格（`w`/`h` 在地图节点上）。
- **`cost` / `gate`**（可选）：和道路**同一套字段**（§4.5.1）——
  建筑加上 `gate: { tags: [钥匙] }` 就是一扇**锁着的门**，`cost` 也能扣血扣蓝。
  机制完全复用，不另发明。
- **`point_reward`**（可选）：结算时给玩家**几点自由属性点**（默认 0）——和怪物共用同一个字段（§4.8.8）。
- `encounter`: `empty | treasure | monster | event | shop | talk`（基础行为，**六种**）

| `encounter` | 玩家踩到时发生什么 | 用哪些字段 |
|---|---|---|
| `empty` | 什么都不发生（纯装饰 / 占位） | — |
| `treasure` | 开箱给东西 | `reward_pool` ＋ `pick` / `copies` ＋ `mimic` |
| `monster` | 抽一只怪开打 | `monster_pool` |
| **`event`** | **门槛 ＋ 判定 ＋ 后果**（撬锁 / 陷阱 / 谜题 / 抉择） | **`event`**（§4.8.9） |
| **`shop`** | **用钱换东西** | **`stock` ＋ `price`**（§4.8.11） |
| **`talk`** | **与建筑里的 NPC 对话**（逐条台词 ＋ 树状选项，可给出道具） | **`npcs` ＋ `dialog`，写在建筑实例（地图节点）上**（§4.9） |

> **六种行为是并列的，不互相嵌套。** 想表达"锁着的宝箱屋"＝ `encounter: event` 的门槛 + 成功后 `goto`/`grant`；
> 想表达"打怪后开店"属于 P1 的复合事件，M1 不做。
> `talk` 与其它五种同样并列：**对话本身不判定、不给属性点**，要发东西就在对话树的 `prop` 结局里发道具（§4.9.4）。

- `event`（`encounter=event` 时）：**事件块** —— 门槛 `gate` ＋ 判定 `check` ＋ 后果 `on_success` / `on_fail`（完整结构见 §4.8.9）
- `stock` / `price`（`encounter=shop` 时）：**上架池 + 定价**（完整结构见 §4.8.11）；不写 `price` 就用前置配置 `shop.price`
- `reward_pool`（treasure 时）：奖励池，可混装备与消耗品（§4.8.5①）：
  ```yaml
  reward_pool:
    source: ids                 # ids = 手选 | filter = 从整个组件库里筛
    ids: [{ id: red_potion, weight: 5 }, { id: iron_sword, weight: 1 }]
    # source: filter 时写 filter: { itemKind: consumable, tags: [common] }
  ```
  **只保留其中"已启用"的道具**。
- `pick` / `copies`（可选）：**覆盖**前置配置的 `treasure` 抽取算法；**算法不写在建筑上**，写在 §4.8.6 的前置配置里。
- **`monster_pool`**（`encounter=monster` 时）：**怪物池，不是单只**（§4.8.5⑥）：
  ```yaml
  monster_pool:
    source: ids                 # ids = 手选 | filter = 从整个组件库里筛
    ids: [{ id: goblin, weight: 3 }, { id: slime, weight: 1 }]
    # source: filter 时写 filter: { tags: [cave] }
  ```
  踩到时**掷骰按权重抽一只**，再摇它的属性，然后开打。**想让房间固定出哥布林就只放哥布林**——单只 = 单元素池，不需要另开字段。
- `mimic`（可选）：`{ chance: 0~1, monster: id, reward_pool }`
  - **宝箱怪物机制**：在宝箱屋（`encounter=treasure`）下勾选后出现；按 `chance` 判定——命中则实为伪装怪物（先战斗），
    战胜后走**战利品算法 `loot`**；未命中走普通 `treasure` 开箱算法。
  - 这里用单只 `monster`（伪装成"这一个箱子里的那只怪"），不用池。
- `desc`

> **算法只在前置配置里定义一次**（§4.8.6 的 `treasure` / `loot`）：建筑和怪物**只提供"池"**，
> 想换算法就覆盖 `pick` / `copies`，不重复发明一套。

### 4.5 道路 `road`

道路是**地形件**：它不触发遭遇（那是建筑的事），它只回答两个问题——
**"走过去要付什么？"（消耗）** 和 **"凭什么能过去？"（权限）**。

#### 4.5.1 两个正交维度

| 维度 | 字段 | 含义 | 回答 |
|---|---|---|---|
| **消耗 `cost`** | 走这一格要付出什么 | 数值型资源扣减 | "走过去有多贵" |
| **权限 `gate`** | 走这一格需要什么 | 标签匹配 | "你有没有资格过去" |

**消耗 `cost`（可扣的资源就这三种）**

| 资源 | 字段 | 例 |
|---|---|---|
| 步数 | `step` | 沼泽 `2`；传送带 `0` |
| 血量 | `hp` | 荆棘路 `3` |
| 法力 | `mp` | 法术结界 `2` |

**权限 `gate`（标签匹配，不写死任何词）**

```yaml
gate:
  tags: [火抗]           # 需要哪些标签（默认"有任一即可"）
  mode: any              # any = 任一即可（默认） | all = 全都要
  missing: penalty       # 不满足时怎么办：block = 走不进去 | penalty = 能走但加罚
  penalty: { hp: 5 }     # missing=penalty 时的额外消耗
```

**完整写法**

```yaml
- id: swamp                  # 纯消耗：难行
  name: 沼泽
  icon: 🟫
  cost: { step: 2 }

- id: river                  # 消耗 + 硬权限：没船过不去
  name: 河流
  icon: 🌊
  cost: { step: 1 }
  gate: { tags: [渡河], missing: block }

- id: volcano                # 消耗 + 软权限：没火抗也能进，但掉血
  name: 火焰山
  icon: 🌋
  cost: { step: 1 }
  gate: { tags: [火抗], missing: penalty, penalty: { hp: 5 } }
```

#### 4.5.2 匹配机制（能力 = 标签集合）

```text
① 算玩家能力      capabilities = ⋃(穿戴中装备.tags) ∪ 当前职业.tags
② 看这一段路      gate = 这条道路的 gate（没写 gate 就直接通过）
③ 匹配            满足 = (gate.tags ∩ capabilities ≠ ∅)        ← mode: any
                        (gate.tags ⊆ capabilities)              ← mode: all
④ 分支            满足    → 按 cost 扣资源，走进这一格
                  不满足  → missing: block   → 走不进去
                            missing: penalty → 按 cost + penalty 一起扣
```

**能力只从"穿戴中装备"和"当前职业"来**（不做背包里带着就算、也不做消耗品当长期钥匙）：

- 想让某样东西当钥匙 → **把它做成装备**。小船占"手"、火抗鞋占"脚"，天然合理。
- 消耗品是一次性的，做不了长期权限，不进能力集合。

#### 4.5.3 为什么用标签，而不是写死"渡河""火抗"

因为**写死就把玩法框死了**。用标签，编辑器**不认识任何具体的词**，但机制照样成立：

| 你想做的 | 道路写 | 玩家需要拿出 |
|---|---|---|
| 河流 | `gate.tags: [渡河]` | 小船（`tags: [渡河]`） |
| 火焰山 | `gate.tags: [火抗]` | 火抗鞋（`tags: [火抗]`） |
| 毒沼 | `gate.tags: [解毒]` | 解毒草囊（`tags: [解毒]`） |
| 天空桥 | `gate.tags: [飞行]` | 羽翼斗篷（`tags: [飞行]`） |
| 魔障 | `gate.tags: [破魔]` | 破魔符（`tags: [破魔]`） |
| 王城大门 | `gate.tags: [王室]`，`mode: all` | 同时要有印章 + 通行令 |

**"火焰山 + 火抗鞋"是数据组合产生的，不是代码写出来的。** 用户造新标签就自动有新区块，编辑器不用改一行。

#### 4.5.4 记忆点

| 组件 | 消耗 | 权限 | 玩法差异 |
|---|---|---|---|
| 小路 `path` | `step: 1` | — | 基准 |
| 沼泽 `swamp` | `step: 2` | — | 走一格吃掉两步，逼你绕路 / 耗光回合 |
| 传送带 `belt` | `step: 0` | — | 不耗步，等于白走 |
| 河流 `river` | `step: 1` | `[渡河]` `block` | 没船就**过不去**，必须绕路或去获取装备 |
| 火焰山 `volcano` | `step: 1` | `[火抗]` `penalty hp:5` | 强行通过也能过，但**每格掉 5 血**，血量过低则极易败北 |

- **不做的（明确记下来，避免又出现"配了没实现"）**：单向路、踩踏触发遭遇 / 传送。
  想"一踩就出事"就**铺一栋建筑在那格**——不要让道路背上遭遇，否则它就成了第二个建筑。
- 道路**不参与**技能 / `stats` / 力值链，它没有任何属性。
- **`cost` / `gate` 不是道路专属**：它们是**地图件（道路 + 建筑）的公共可选字段**——
  建筑加上 `gate: { tags: [钥匙] }` 就是一扇锁着的门，机制完全复用（§4.4）。

### 4.6 地图 `map`
- `name`
- `start: [x, y]`、`end: [x, y]`（每张图强制恰好一个）
- `nodes`: 每格一个映射 `{ x, y, type, ref?, w?, h? }`；`type ∈ start | end | road | building`：
  - `building` **必须带 `ref`** 指向建筑 id；
  - `road` **也必须带 `ref`** 指向道路 id——因为不同道路的 `cost` / `gate` 不同，不记 ref 就不知道这格要付什么、能不能过；
  - `start` / `end` 是画布内建标记，不带 `ref`。
- **建筑大小 `w`/`h`（单位：格，默认 1）放在地图节点上**，因此同一类型建筑可自由设定不同尺寸（如 2×2 仪式感宝箱屋、巨大的 Boss 宫殿）。**建筑与道路一样作为整块判定**，不再区分入口/出口方位。
- **可走图 = 已放置节点集合**（road + building + start + end），未放置格视为不可通行
- 多图有序；导出/游玩时上一张 `end` 自动成为下一张 `start`

### 4.7 项目 `project`（= 一局游戏的"内容"）

- `name`（= 游戏名）
- `background`（散文）
- `enabledIds`: `string[]` —— 本局**启用**的组件 id（消耗品 / 装备 / 怪物 / 职业 / 技能）
  > **注意这里没有"谁会什么技能"**：那是**游玩态数据**，进 `.psave` 不进 `.pmod`（§4.8.3）。
- `rules`: `{ move, combat, treasure, loot, class_pool }` —— **这一局的规则（前置配置）**，
  每个场景一套算法，完整清单见 **§4.8.6**
- `maps`: `map[]`（= 左栏「图层」列表，有序；建筑 / 道路的"铺设"就存在这里）

> **组件库不是 `project` 的一部分。** 库存独立的 localStorage key（`poprpg_library`），跨项目共享、长期存活，
> 里面同时装着系统预设和用户自建。`project` 只记"这一局用了库里的哪些"，**不存组件定义本身**；
> 因此改了库里的哥布林，所有用到它的局都会跟着变——这正是"库是工具来源"该有的行为。
>
> 导出 `.pmod` 时，把**用到的定义快照**嵌进 `## 设定` 段（§3.3），让文件自包含；
> 别人导入后这些定义**并入他自己的组件库**，之后就是他自己的资产了。

> **皮肤库同样不是 `project` 的一部分（裁决 15）。** 用户**导入过**的 `.pp` 各为一条皮肤记录，跨项目共享、
> 长期存活；**游戏自带（`.pgame` 内）的皮肤不入库**——它只随该局加载。条目索引（名称／作者／来源／导入时间／是否启用）
> 存 `localStorage`（key `poprpg_skins`），**包体（二进制 zip）存 IndexedDB**——`localStorage` 只能存字符串、
> 配额约 5 MB，不适合包体（[`08-deploy.md`](08-deploy.md) §9）。
> **运行时一次只解压一套**：内存中只保留当前生效皮肤的解压结果，切换皮肤时**先清空当前解压结果**再解压新的
> （[`skin/00-package.md`](skin/00-package.md) §4.4）。

### 4.9 NPC 与对话（第 8 类组件）

> **编号说明**：§4.8 已被**规则引擎**占用（在 [`03-engine.md`](03-engine.md)），本类不抢该编号，故顺延为 §4.9。
> NPC 是继既有各类之后的**第 8 类结构化组件**（§4.0 的公共字段它全有），在 `## 设定` 里是 `### NPC` 段（§3.1）。

NPC 与道具／技能同类，属**非地图件**（不铺地图格），但多一条**落点约束**：

- **NPC 只能出现在建筑里**——不能单独站在地图格上、不能凭空触发。
- 因此 NPC **不走 `enabledIds` 启用**（§3.3）：它的**入包条件是"被某个建筑实例引用"**。
- 引用写在**建筑实例（地图节点）**上，而**不是建筑定义**上：同一栋「客栈」铺到多格，各格可以遇到不同的人。

#### 4.9.1 NPC 定义 `npc`

| 字段 | 含义 |
|---|---|
| `id` / `name` / `icon` / `tags` / `desc` | 与其他组件一致（§4.0） |
| `dialogs` | **多套对话方案**：`{ <方案名>: 节点[] }`，**方案名即 key**（如 `Mod1` / `Mod2`）。树结构见 §4.9.2 |

- **NPC 自身不含"出现在哪里"**：位置一律由建筑实例给出（§4.9.3）。
- NPC 的**地图形象与立绘**属素材侧（[`skin/02-role.md`](skin/02-role.md) §三 / §四），不在本文件。

#### 4.9.2 对话树结构

**一套"方案（Mod）"＝ 一棵对话树**。顶层对象的 key 是方案名，值是该方案的**根节点数组**（按顺序展示，通常只写一个）。

**节点（Node）**

| 字段 | 类型 | 含义 |
|---|---|---|
| `message` | `string[]` | NPC 台词，**按顺序逐条展示**，玩家点击「继续」推进 |
| `items` | 项[] | 子项：**选项分支 `chat`** 或 **道具结局 `prop`**；**空数组即对话到此结束** |
| `dice` | `string`（可省） | **该节点选项的抽取骰**（如 `1D6`）。**有此字段 → 本节点的 `items` 要靠掷骰命中**（见下）；**没有 → 玩家直接点选**。写在**内容**里，不是前置配置 |
| `result` | `string` | 节点级：**编辑器用的节点标题**（可省、运行时不展示）；项级 `result` 见下表 |

**项（`items` 的元素）**

| `type` | 字段 | 含义 |
|---|---|---|
| `chat` | `result` ＋ `message` ＋ `items` ＋（`hit`） | **玩家选项**：`result` 是选项按钮文本；点击后展示该 `message`；其 `items` 非空即继续下一层，为空即结束 |
| `prop` | `result` ＋ `items` ＋（`hit`） | **给道具并结束**：`items` 是**道具 id 列表**，**可重复**（同一种给 2 份就写 2 次）；`result` 是编辑器用的说明文本，运行时不展示 |
| 共有 | `hit` | **骰子命中区间**（如 `"1-2"` / `"3-4"` / `"5-6"`，也可单点 `"6"`）。**仅在父节点写了 `dice` 时使用**；父节点无 `dice` 的项不写 `hit` |

**选项怎么被选中（`dice` / `hit`）**

| 情形 | 玩家看到什么 | 规则 |
|---|---|---|
| 节点**写了 `dice`** | **一个「掷骰」按钮**，不直接给选项列表 | 玩家掷 `dice` → 拿点数去各 `hit` 区间里找**唯一命中项** → 命中 `chat` 就进它的分支、命中 `prop` 就给道具并结束 |
| 掷出点数**落在所有 `hit` 之外**（空档） | 提示"未命中"，**再给一次掷骰** | **未命中即可再掷**，直到命中为止（不会卡死；编辑器会提示有空洞，见下） |
| 节点**没写 `dice`** | **选项列表直接可点** | 沿用原有行为：玩家自己点一个 `chat`，或选到 `prop` 就结束 |

**重复进入与"一次性交付"**

- **方案锁定**：选 NPC、选方案两级各掷一次 `talk.dice`（§4.9.3），**一旦掷定，本局永久不变**——同一建筑实例重踩／回访，**不再重掷、不再切人、不再换方案**。
- **`prop` 交付即终态**：某个 `prop` 节点已经把道具发出去后，**再次**和这位 NPC 对话时，**只回放那个交付节点的 `message`**（逐条展示后关闭），**不再出现 `items`（选项 / 掷骰按钮都没有）、不再给道具**——这是**防刷道具**的闸门。
- 终态以**建筑实例**为单位记录（与"抽定不变"同源，写进 `.psave`）：记录"已交付的节点 + 是否已交付"，读取时按此回放。

```yaml
dialogs:
  Mod1:                                    # 方案名（多套方案之一，§4.9.3）
    - result: 开场                         # 节点标题（编辑器用，运行时不展示）
      message: ["地穴的入口已被封了三代。", "你若执意下去，先听我一句。"]
      dice: 1D6                            # 写了 dice：这层选项靠掷骰命中（不给直接点选）
      items:
        - type: chat                       # 选项 A
          hit: "1-2"                       # 掷出 1~2 命中它
          result: "A：我想知道那扇门后面有什么。"
          message: ["门后是路，路上是选择。"]
          items:
            - type: chat                   # 下一层可继续嵌套；这层没写 dice → 玩家直接点选
              result: "A1：那我应该走哪条？"
              message: ["走你想走的。"]
              items: []
        - type: chat                       # 选项 B：选项数量不定
          hit: "3-4"
          result: "B：我只是路过。"
          message: ["那就慢走。"]
          items: []
        - type: prop                       # 结局：给道具后结束（同种写两次＝给两份）
          hit: "5-6"
          result: "C：这些你带上。"
          items: [red_potion, red_potion, blue_potion]
  Mod2:
    - message: ["又见面了。"]              # 不写 dice：选项列表直接可点
      items: []
```

**结构约束**

| 约束 | 规则 | 违反时 |
|---|---|---|
| **树状、无回边** | 子节点只向下生长，**不能指回祖先**；不存在"跳转 / 循环 / 条件"字段——这是**树**而非图 | 编辑器不提供回环连线；导入含回边的包时按树解析、丢弃回边并提示 |
| **`prop` 为终止项** | 节点的 `items` 里出现 `prop` 即**该节点对话结束**（先结算全部 `prop`）；`prop` **不与 `chat` 混排** | 混排时按"`prop` 优先结算并结束对话"处理，并给校验提示 |
| **`dice` 的 `hit` 必须可命中** | 节点写了 `dice` 时，其中每个项都应带 `hit`；各 `hit` 的**并集应覆盖该骰子的全部点数**，不留空档 | **只提示、不拦截**：编辑器算出"未覆盖的点数"并标黄"掷到 X 会落空、运行时需重掷"（§5.7；导入的包若留空档，运行时按"未命中再掷"处理） |
| **`hit` 从属于 `dice`** | `hit` 只在**父节点写了 `dice`** 时有意义 | 父节点无 `dice` 却写了 `hit` → 该字段被忽略并提示（该项仍走"直接点选"） |
| **命中唯一** | 同一节点内各 `hit` **不应重叠** | 编辑器提示重叠；运行时按**先出现的 `hit` 优先**命中（建议改掉） |
| **`message` 顺序** | 逐条展示，玩家点击继续；**不做打字机 / 逐字动画**（V1） | — |
| **道具引用** | `prop.items` 的元素必须是**已存在且已启用**的道具 id | 悬空引用按 §5.7 提示；给出的份数照 `items` 重复次数计 |
| **不给属性点** | 对话不提供 `point_reward`，也不判定 | 要发东西就用 `prop` 发道具（§4.9.4） |
| **一次性交付** | `prop` 结算后该实例对话进入**终态**，再次进入**只回放交付节点的 `message`**、不再给道具 | 重刷道具由"终态记录"拦住（见上"重复进入"） |

#### 4.9.3 建筑实例上的 NPC 与方案

**建筑实例＝地图节点**（§4.6）。NPC 的挂载与选择**写在节点上**：

```yaml
- { x: 2, y: 0, type: building, ref: inn, npcs: [elder, merchant] }
```

| 字段 | 写在哪 | 含义 |
|---|---|---|
| `encounter: talk` | **建筑定义**（§4.4，六种行为之一） | 该建筑的**建筑事件阶段留空**、**以对话为主体**（对话本身由实例的 `npcs` 触发，见下） |
| `npcs` | **建筑实例（地图节点）** | NPC 候选 id 数组：**不写 ＝ 不触发对话**（该建筑只跑自己的建筑事件）；**写 1 位 ＝ 固定**；**写多位 ＝ 多选一，掷骰决定** |
| `dialog` | **建筑实例（地图节点）** | 指定启用**哪一套对话方案**（方案名）。**不写**：该 NPC 只有一套方案 → 用它；**有多套 → 掷骰决定** |

**触发时机（V2.0 追加设定）**：**进入建筑之后、建筑事件之前**——踩到建筑 → ① **NPC 触发**（本节）→ ② **建筑事件**（该建筑自己的 `encounter` 行为）。
因此 **`npcs` 与 `encounter` 正交**：`npcs` 可挂在**任何建筑实例**上（不再限于 `talk` 建筑）；**`encounter: talk` ＝ 建筑事件阶段留空、以对话为主体**的建筑。见 [`07-decisions.md`](07-decisions.md) §8.3。

**只在「进入建筑」时触发一次**：触发条件是**玩家从建筑外的格子踏入该建筑（任意一格）**；**已经在建筑内部移动（多格建筑里从一个格走到另一个格）不再触发**——多格建筑是**同一座**（同一节点 key），只在**首次踏入**算"进入"。**首次进入一定走对话流程**。

**重入（该实例已触发过一次对话）**：再次进入**不直接进对话**，先弹**选择对话框**——列出**已锁定的那位 NPC 的名字**（点它 ＝ **重看**该对话）＋「**直接进入**」（跳过对话，直接跑建筑事件 / 离开）。**掷定即锁死不变**：列表**不换人、不重掷**；**已交付**（`prop` 终态）的实例点名字时只回放**交付节点的 `message`**。

**与 `treasure` 的关系**：宝箱**没配奖励池**（或池抽到 0 件）**但配了 NPC** → 进入时**不再提示"什么也没有 / 已经空了"**——**NPC 就是它的内容物**（§4.8.5⑥）。

**抽取规则（两级，各自独立掷骰）**

1. **选 NPC**：`npcs` 长度 ＝ 1 → 直接取；> 1 → **按位置等权**掷骰抽一位。
2. **选方案**：该 NPC 的 `dialogs` 方案数 ＝ 1 → 直接取；> 1 → **等权**掷骰抽一套。

- 两次都用**对话骰**（前置配置 `talk.dice`，缺省 `1D6`，与 `event.dice` 同款，§4.8.6）；踩到时各掷一次，**同一实例整场不重掷**（与"怪物登场掷骰一次摇定"同一原则）。
- **掷定即锁死**：只要这一步**由骰子决定过**（`npcs` 多位、或方案多套），**本局永久锁定**——之后重踩／回访该实例，**不再重掷、不再换人、不再换方案**。锁的是**实例**（不是 NPC 全局）：同一 NPC 出现在两栋建筑里，各自独立抽。
- `dialog` **写死方案名时跳过第 2 步、不掷骰**（写死的方案自然也不变）；写了一个不存在的方案名 → 悬空引用，按 §5.7 提示并**降级为掷骰**。
- **`encounter: talk` 与 `npcs` 缺一不可**：定义是 `talk` 但实例没写 `npcs`（或写空数组）→ 该建筑**无对话**，视为 `empty`；实例写了 `npcs` 但定义不是 `talk` → 该字段**不生效**并提示。
- **交付终态**：一旦该实例的对话走到 `prop` 结局并发出道具，记为**已交付**（§4.9.2）；此后再次进入**只回放交付节点的 `message`**，既不重掷方案也不再发道具。

#### 4.9.4 与其他机制的关系

- **道具来源**：`prop` 给出的道具进背包，仍受 `inventory_size` 约束（§4.2.4，满则拒绝并提示）；**同一位 NPC 只交付一次**（§4.9.2 一次性交付）。
- **两种骰子分属两层**：`talk.dice`（选人 / 选方案）是**前置配置**；节点上的 `dice`（选项抽取）是**内容**（和事件的 `check.dice` 一样写在组件里），不改配置项总账。
- **进不进存档**：本局**抽定的 NPC / 方案**与**已交付的节点**都写进 `.psave`（按建筑实例），重开新局自然重置。
- **与 `event` 的区别**：事件（§4.8.9）是"门槛 ＋ 判定 ＋ 后果"的**一次结算**；对话是**逐条台词 ＋ 树状选项**的**多轮交互**。二者都属建筑遭遇，但**不互相嵌套**（沿用 §4.4「行为并列」的立场）。
- **与 `shop` 的区别**：交易在 `shop` 里做（§4.8.11）；对话**不开放货架**，要送东西用 `prop`。
- **不产生结局**：对话**不改变通关条件、不记剧情旗标、不设多结局**——把"剧情分支树"划在范围外（§7.4）。
