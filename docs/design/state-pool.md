# PopRPG 设计文档 — 模块：state-pool（全局状态池）

> **性质**：**V2.x 追加设定 / 结构改造**，不属于 V1 的阶段性设计。与 V2.0「NPC 与对话」同档：属**结构改造类**，具备"重写数据结构"的授权（本引擎**没有存量用户**，故不做旧档兼容迁移，只做读取容错）。
>
> **定位**：本文件是**全局状态池的唯一权威口径**。`.pmod` 的声明段、编辑器的定义面板、运行时求值、校验条目一律以本文件为准；[`07-decisions.md`](07-decisions.md) §8.5 登记对应裁决（裁决 31 起）。
>
> **上位规范继续有效**：V1 口径（七大类 · 13 项配置 · `encounter` 五选一）与 V2.0 口径（第 8 类 NPC · 14 项配置 · 六选一行为）**不改写**；本文件只在其上追加。
>
> **为什么需要它**：V1 / V2.0 的反馈是**一次性**的——同一处内容第二次进入与第一次完全一样，没有"因为先前的行为而改变"的通道。全局状态池提供**同一处内容随状态变化**的通道，是后续「建筑与 NPC 的布尔判定树（基于状态的反馈切换）」的前置结构。

## 一、基本设定

### 1.1 一句话定义

**全局状态池 ＝ 一张全局唯一、全局可见的键值表**，存放本局运行期间的全部可变状态；**所有操作（对话、门锁、建筑触发、每回合结算）一律通过读算子查询它、通过写算子修改它**。

### 1.2 三个类型

| 类型 | 取值 | 说明 |
|---|---|---|
| `string` | 文本 | 无长度上限；空串是合法值 |
| `number` | 有限数值 | 不做整数限定；不设上下限（由作者的算子逻辑自洽） |
| `boolean` | `true` / `false` | 只有两个字面量 |

- **没有第四种类型**，**没有数组与对象**。需要列表语义时用 `string` ＋ `contain` 近似，或拆成多个 `boolean`。
- 类型是**声明项的一部分**：一个键的类型在声明处定死，**运行期不可改**；写算子与声明类型不符即为非法配置（§十）。

### 1.3 全局唯一与全局可见

- **全局唯一**：同一个键在一局之内只有一处存储。不存在"某个 NPC 自己的副本"——任何使用处读到的都是同一份值。
- **全局可见**：任何使用处（任意 NPC 的任意记录、任意门锁、任意建筑、**每回合开始时的回合判定**）都可以读、可以写同一个键，**不需要任何声明 / 引用 / 授权手续**。
- **一局一份**：池随开局建立、随存档保存；`.pmod` 里的声明**只提供初值与类型**，不提供运行期副本。

> **与 `Rules.state` 的区别（命名与语义都要分清）**：`Rules.state`（`max_duration`，[`03-engine.md`](03-engine.md) §4.8.10）是**挂在单位上的状态效果**（标签 ＋ 剩余回合数 ＋ 每回合增减），随回合递减、到期移除。
> 本文件的"状态池"是**键值表**，键值本身**不会自动衰减**（衰减只能由作者写"回合判定"来 tick，§五 / §八）。两者**不是同一件事**，代码与文案中**不得用"状态"二字单独指代本池**——本池一律称**状态池**，其变量称**池变量**。

### 1.4 判定：一切操作的统一入口

**状态池只提供"读 / 写"两个接口；"什么时候读、什么时候写"由判定决定。**判定按触发时机分两类（完整口径见 §五）：

| 判定 | 触发时机 | 声明处 |
|---|---|---|
| **回合判定** | **每回合开始时**触发一次 | `.pmod` 的 `## Pool` 段（`checks` 列表） |
| **触发判定** | **事件触发时**触发（NPC 对话、建筑触发、门锁……） | 使用处**就地内联** |

## 二、命名空间与前缀隔离

### 2.1 两个空间

池的键**一律由"空间词 ＋ 短名"组成**，中间以 `-` 连接：

| 空间 | 前缀 | 归属 | 写入者 | 声明者 |
|---|---|---|---|---|
| 引擎空间 | `engine-` | 引擎内部状态（含主角六维、步数、位置、道具件数） | **只有引擎** | 引擎（不落 `.pmod`） |
| 作者空间 | `usr-` | 作者声明的池变量 | 引擎与使用处 | `.pmod` 的 `## Pool` |

- **规范全名**：`engine-aaa` / `usr-aaa`。短名（`aaa`）**不是全名**，只在编辑器输入框里出现。
- 短名不得为空。短名含 `-` 时编辑器提示改用下划线，避免与空间词混淆。
- 两个空间**互不覆盖**：`engine-aaa` 与 `usr-aaa` 是**两个键**。

### 2.2 声明侧的强制前缀（防覆写）

**`.pmod` 的 `## Pool` 里声明的每一个键，一律无条件追加 `usr-` 前缀。**

| 作者写下 | 落盘结果 |
|---|---|
| `aaa` | `usr-aaa` |
| `engine-aaa` | `usr-engine-aaa` |
| `usr-aaa` | `usr-aaa`（已带前缀，不重复追加） |

> **这一条是防覆写的硬保障**：作者无论怎么写，都**不可能**在 `.pmod` 里声明出一个 `engine-` 空间的键，因此**不可能覆写引擎状态**。引擎空间的键**只**由引擎建立。

### 2.3 引用侧的全名匹配

使用处（对话记录的判定 / 修改、门锁的判定、回合判定）里的键名**按规范全名精确匹配**，**不做前缀补齐**。

- 引用 `usr-aaa` → 命中作者空间的 `aaa`。
- 引用 `engine-hpMax` → 命中引擎空间的主角生命上限。
- 引用不存在的全名 → 校验项 `K20` 提示（§十）；运行时该条判定**视为不成立**、该条修改**不执行**（与"门锁标签无人具备"同档：不崩溃、不静默改数）。

**编辑器的写法约定**（§九）：在对象设置面板里，作者只写**短名**与**空间选择**；编辑器负责拼成规范全名后落盘。默认空间为 `usr`。

**与读写接口的关系**（§2.5）：落盘的规范全名在装载时会拆回 `(space, 短名)`（`engine-` → `engine`、`usr-` → `usr`），运行时再由接口按 `space` 拼回前缀调用——**全名匹配与空间参数化两条路等价**，只是"人读的文件形态"与"代码的调用形态"不同。

### 2.4 容错（手写文件）

对**手工编辑的 `.pmod`**（不经编辑器产出）：

| 情形 | 处理 |
|---|---|
| 声明里出现**无前后缀**的名字（如 `aaa`） | 按 `usr-aaa` 补齐，导入提示里说明一句 |
| 声明里出现 `engine-` 开头的名字 | 改写为 `usr-engine-`（§2.2）并**提示一句**"该名字已归入作者空间" |
| 引用里出现**无前后缀**的名字 | 按 `usr-` 补齐后匹配；仍匹配不到再出 `K20` |
| 引用里出现 `engine-` 开头的名字 | 按引擎空间读取；读得到即可用，读不到出 `K20` |

### 2.5 读写接口：空间参数化（存储不分空间）

**存储层与接口层要分开看——这是本节的核心：**

- **存储不分空间**：运行时的池是**一张扁平表** `Record<规范全名, 值>`（§8.1），**不按空间分区、不分两个容器**。规范全名（`engine-xxx` / `usr-xxx`）就是唯一的键。
- **接口按空间参数化**：读接口与写接口都**显式带一个 `space` 参数**，`space ∈ { engine, usr }`：

  | 接口 | 调用形状 | 内部行为 |
  |---|---|---|
  | 读 | `read(space, key)` | 按 `space` 拼前缀 → 规范全名 → 在扁平表取值 |
  | 写 | `write(space, key, op, value)` | 同上，写回扁平表 |

- **`space` 的唯一作用就是"自动追加不同的 key 前缀"**：`engine` → `engine-`，`usr` → `usr-`。`read(engine, 'hpValue')` 读的是 `engine-hpValue`，`read(usr, 'hpValue')` 读的是 `usr-hpValue`；**两者是两个键**（§2.1）。
- **为什么这样分**：存储层保持"只有一个命名空间"的简单性（前缀就是普通字符，不需要容器映射）；接口层的 `space` 参数承担"作者只写短名、由引擎补前缀"的便利与"两空间不可能互相覆盖"的保证。
- **声明登记表（索引）仍是运行期派生结构**（不落盘、不进存档）：`规范全名 → { 空间, 类型, 初值, 来源, 写权限 }`（来源 ＝ `engine` / `pmod`）。它**不再是读接口的前置**（读接口只认扁平表），而是给**类型解析、写权限校验（§3.5）与编辑器自动化（§九）**用：类型推断、引用数统计、自动联想、`K20` 比对全部读它。每局开局按"引擎键 ＋ 当次 `## Pool` 声明"重建。
- **`.pmod` 落盘仍写规范全名**（便于人读、便于精确匹配，§2.3）；导入 / 导出时在"规范全名"与"`(space, 短名)`"之间互相转换。手写文件按 §2.4 补齐并提示。

### 2.6 引擎变量清单的权威性

**§三的总表是 `engine-` 空间键的唯一权威清单**。它的作用有三：

- 引擎播种时按它建立 `engine-` 键；
- 编辑器变量表格按它**逐行展示内置变量**（并打「引擎」tag，§9.2）；
- 运行时对 `engine-` 引用的 `K20` 判定按它比对（表外即"引擎无此变量"）。

**`engine-` 空间新增键必须同步登记本表**（§3 末注）。

## 三、引擎空间（`engine-`）变量总表

> **命名定稿**：以下键名（含六维 `hpValue` / `hpMax` / `mpValue` / `mpMax` / `patk` / `matk` / `pdef` / `mdef`）**已定稿**，不再改动。

### 3.1 主角六维属性（并入本池）

主角的属性与资源**整体并入本池**，此前分散在单位对象上的两处存储（已结算属性值 / 当前资源值）**退役**，池是唯一储存处。

| 规范全名 | 类型 | 含义 | 来源 |
|---|---|---|---|
| `engine-hpValue` | `number` | 当前生命值 | 开局由职业给起点，运行期由战斗与道具增减 |
| `engine-hpMax` | `number` | 生命上限 | 职业 `base_stats` ＋ 玩家分配点 |
| `engine-mpValue` | `number` | 当前法力值 | 开局满值，运行期由技能消耗与道具恢复 |
| `engine-mpMax` | `number` | 法力上限 | 职业 `base_stats` ＋ 玩家分配点 |
| `engine-patk` | `number` | 物理攻击 | 职业 `base_stats` ＋ 分配点（②装备 / ②状态加成在力值链②环**读取时**叠加，**不进本键**） |
| `engine-matk` | `number` | 魔法攻击 | 同上 |
| `engine-pdef` | `number` | 物理防御 | 同上 |
| `engine-mdef` | `number` | 魔法防御 | 同上 |

- **只有 `hp` / `mp` 分"当前值"与"上限"两个键**；四能力只有一个键（它们的上限即其数值本身）。
- **四能力键存①基础属性**（职业 `base_stats` ＋ 分配点），与既有 `Unit.stats` / `buildPower` 一致；②装备 / ③职业百分比 / ②状态 `modifiers` 仍在力值链各环**读取时**叠加，不预先合进本键 —— 这样四能力既有池里的镜面（可供 `if` / 观察读取），又不与力值链重复计。
- 力值合成链（属性 ＋ 装备 ＋ 职业百分比 ＋ 状态 `modifiers`，[`03-engine.md`](03-engine.md) §4.8.2）**不改算法**，只改**读法与写法**：读的是池的键，写回也是池的键。
- `engine-hpValue` / `engine-mpValue` 降到 `0` 或以下 **不触发任何池事件**：败北判定仍由既有回合流程负责（§4.8.0 硬规则），池只提供数字。

### 3.2 引擎核心状态

引擎自身的运行期状态同样落在此空间；**键名以下表为准**（作者不得声明、不得覆写，§2.2）。

| 规范全名 | 类型 | 含义 |
|---|---|---|
| `engine-class` | `string` | 本局主人公的职业组件 `id` |
| `engine-points` | `number` | 尚未分配的属性点 |
| `engine-round` | `number` | 当前回合数（每推进一次时间 +1） |
| `engine-steps` | `number` | **本局累计真实步数**（走一格 `+1`，**来回绕圈也照加**，只增不减） |
| `engine-stepsLeft` | `number` | **本回合剩余步数**（本回合掷骰所得，走一格 `-1`，回合结束归零） |
| `engine-pos` | `string` | **玩家当前位置的规范串**（形状见 §3.3） |
| `engine-mapIndex` | `number` | 当前所在地图下标 |
| `engine-inventoryUsed` | `number` | 背包已占用的格数 |
| `engine-inventorySize` | `number` | 背包容量（＝职业上一个数字） |
| `engine-roll.npc.<建筑实例 key>.<slotN>` | `string` | **NPC 槽位的抽定结果**：值为该槽位落地的 npc 组件 `id`（**§3.6**） |
| `engine-roll.mod.<建筑实例 key>.<npcId>.<modId>` | `boolean` | **某位 NPC 的某套对话方案是否已执行完**：引擎执行完该套方案即写 `true`（**§3.6**） |
| ~~`engine-talk.<建筑实例 key>.<标记>`~~ | — | **退役**（原对话进度标记 `cursor` / `talkDone` / `deliveredNode`）：不再由引擎内置记账，改由 `engine-roll.mod.*` 记录 ＋ 作者 `if` / 判定模板表达（§3.6 / §6.7，**裁决 54 / 61**） |
| ~~`engine-once.<建筑实例 key>`~~ | — | **退役**（原一次性建筑 / 格子标记）：改由预设判定 / 判定模板表达（**裁决 54** / **裁决 56**） |

- **`engine-steps` 与 `engine-pos` 是两个独立的键**：这正是为了区分"玩家来回绕圈"的场景——**走的路越多，`engine-steps` 越大，但 `engine-pos` 可能回到起点**。作者要"以真实步数计费 / 计时"读 `engine-steps`；要"按所在地点触发反馈"读 `engine-pos`。
- **建筑实例 key 的形状不变**（`<地图名>#<ref>@<锚点>`，[`07-decisions.md`](07-decisions.md) §8.3 设定 2）。
- **`engine-roll.*` 的记账蓝本见 §3.6**：**抽定按槽位**（值 ＝ 落地的 npc `id`）、**执行记录按人 ＋ 方案**（值 ＝ `true`），两者**都由引擎写**、作者只读。
- **键名粒度以本表为准**；`engine-` 空间新增键**必须同步登记本表**。

### 3.3 玩家位置串 `engine-pos`

- **粒度 ＝ "地图-XY"**：形状 `"<地图>-<x>,<y>"`，如 `"0-3,5"`（地图下标 `0`，第 3 列第 5 行）。
- `<地图>` 与 `engine-mapIndex` 同源；`<x>,<y>` 是玩家**当前所站格**的坐标（站在建筑上时取该建筑占据格的**左上角**坐标；建筑身份可由坐标反查地图节点）。
- 起点 / 终点 / 道路格 / 建筑格一视同仁——位置串只表达"站在哪一格"。
- **只读**：位置由移动流程写入，作者**不可写**（§3.5）。

### 3.4 道具持有数量（并入本池）

道具的**持有件数**同样落入池，作为可被任意使用处读取与观察的引擎状态：

| 规范全名 | 类型 | 含义 |
|---|---|---|
| `engine-item.<道具 id>` | `number` | 玩家**当前持有的该道具件数**（同一 id 的份数；背包与已穿戴合并计） |

- **未持有 ＝ 键不存在**：读取不存在的 `engine-item.<道具 id>` **一律得 `0`**（不报 `K20`；这是引擎键的特例——凡以 `engine-item.` 开头的键都按"缺省 0"处理）。
- **入手 / 消耗即写池**：`give`、拾取、购买、使用消耗、丢弃统一走池的写接口；**占用格数继续由件数汇总**（`engine-inventoryUsed` 是派生读数，§3.2）。
- **不设"占用格数"独立键、也不设上限**（**裁决 52**）：一种道具占几格、背包到多少算满，属**玩法层面**的事——作者需要时用**判定模板**自行表达（例：模板 `bag_full = 道具总数 >= 10`，§4.5），引擎不为此增设键、不限制格数。
- **为什么必须入池**：NPC 与建筑常需**按持有的道具数量切换反馈**（"凑齐 3 个苹果我就开门"）。件数只有在池里，才能被 `if` 直接读取、被**观察登记**捕获（§6.5）。
- **货币不是独立的引擎参数**：金 / 银等货币是游戏**预设道具**之一，与普通道具**同走 `engine-item.<道具 id>`**（如 `engine-item.gold`），**不设 `engine-gold` 之类的专用键**——它不属于引擎参数项。

### 3.5 只读与可写约束

- 作者声明**不可能**落入 `engine-` 空间（§2.2）。
- 作者的使用处**可以读** `engine-` 的全部键；**可以写**以下四类**数值型**键，其余 `engine-` 键**只读**——写了即出 `K23`（§十），运行时不执行：
  - 六维中的资源：`engine-hpValue` / `engine-mpValue`（对话赠予与代价要用到）；
  - 成长：`engine-points`；
  - **道具件数**：`engine-item.<道具 id>`（赠予 / 扣减要用到）；
  - **本回合剩余步数**：`engine-stepsLeft`（"额外走一步 / 少走一步"这类反馈要用到；这是游戏的一部分，故开放写入，**裁决 51**）。
- **写引擎键的界面提示**：编辑器在引用 `engine-` 键时固定给出**空间提醒**（"这是引擎变量，写入会影响游戏流程"），使作者清楚自己在写什么——这是"用户向的操作区分空间"的落点（§2.1 / §9.3）。
- **明确只读**：`engine-pos` / `engine-steps` / `engine-mapIndex` / `engine-round` 等**位置与流程类**键——它们由移动与回合流程维护，作者只能读。
- **明确只读（记录类）**：`engine-roll.*`（抽定结果与对话执行记录，§3.6）——由**引擎在执行时写入**，作者**可读不可写**（写即出 `K23`，§十）。作者要以自己的口径记账，就在**作者空间**另立标记键。

### 3.6 抽定与对话执行记录 `engine-roll.*`

V2.0 里"抽定的 NPC / 方案锁死"与"某段对话说过没有"原本由引擎在单位对象 / `.psave` 上另立字段；V2.3 起 **`psave` ＝ 状态表**（§8.6，裁决 55），这两件事一律落池，键族为 `engine-roll.*`，**由引擎写、作者只读**（§3.5）。两者**不是同一件事**：前者记"**抽中了谁**"，后者记"**这套对话走完了**"。

**一、NPC 抽定（记账蓝本是槽位）**

| 项 | 口径 |
|---|---|
| 键 | `engine-roll.npc.<建筑实例 key>.<slotN>` |
| 类型 | `string` |
| 值 | 该槽位本次落地的 **npc 组件 `id`** |
| 槽位从哪来 | 该建筑实例的 **`npcs` 槽位数组**：配了几个槽就有几个槽位，**按声明顺序**编号 `slot0`、`slot1`…（**只配一个槽 ＝ 只有 `slot0`**；两个 ＝ `slot0` ＋ `slot1`）——[`02-data-model.md`](02-data-model.md) §4.9.3 |
| 每个槽位做什么 | 在该槽的 `ids` 里 **N 选 1** —— 落地一位，**值不会是空串**；**该槽 `ids` 为空 ＝ 这个位留空、不建键** |
| 写入时机 | **首次从建筑外踏入该建筑实例**（一次性抽定全部槽位，抽中哪个槽就写哪个槽的键；§4.8.12 阶段 A） |
| 缺省 | **没抽过的槽位 ＝ 键不存在**，读取得空串 `''` —— 这正是"还没抽定"的判据 |

- **为什么以槽位为蓝本、而不是以 npc id 为蓝本**：槽位是**建筑配置**确定的东西（有几个槽、顺序如何），而"抽到谁"是**运行期结果**。记账蓝本必须在**还没抽之前就存在**，否则无从判断"这个槽抽过没有、抽中的是谁"。
- **V2.4 起槽位是真实配置**（**裁决 62**）：实例 `npcs` 的每个元素就是一个槽位（各自的 `ids` / `dialog` / `at`），键形状与"几个槽"**一一对应**——本节与 §4.9.3 同源，**不再有"一位可见"的特殊口径**。`slotN` 是**声明序**：拖动槽位改 `at` **不改号**。
- **同一实例的两个槽各自独立抽**（互相不干扰）；**两个槽抽到同一位 NPC** 时，上面的抽定键各写各的（`slot0` / `slot1` 分别有值），但**第二族（执行记录）会共用同一条** —— 见下方"按人 ＋ 方案"。
- **建筑实例 key 的形状沿用既有口径**：`<地图名>#<ref>@<锚点>`（§3.2 末注 / §4.9.3）。
- **抽定只写一次**：同一实例整场不重掷（[`02-data-model.md`](02-data-model.md) §4.9.3）——键一旦有了值，重入不覆盖。

**二、对话执行记录（按"人 ＋ 方案"）**

| 项 | 口径 |
|---|---|
| 键 | `engine-roll.mod.<建筑实例 key>.<npcId>.<modId>` |
| 类型 | `boolean` |
| 值 | **`true` ＝ 这一位 NPC 的这一套方案已经执行完** |
| 写入时机 | **由引擎写**：mod 的流程由引擎执行，**执行完无脑写 `true`** —— 引擎**不判断**"是否已执行过"，也不做任何拦截 |
| 缺省 | **没执行过 ＝ 键不存在**，读取得 `false` |

- **`<npcId>` 段不可省**：方案名只在"**某一位 NPC 内部**"唯一。同一位 NPC 身上多套对话各记各的 —— 判定通过后从 `Mod1` 换 `Mod2`，`Mod1` 那条**不会拦住** `Mod2`，`Mod2` 也**不会被重复执行**，换回去同理。少了 `<npcId>` 的话，不同人身上的同名方案会**混成一条**。
- **键里不含槽位**（V2.4）：同一实例的**两个槽抽到同一位 NPC** 时，它们**共用这一条记录**——"按人 ＋ 方案记账"的直接结果（**裁决 61 定稿、不推翻**）。要按槽区分，作者在**作者空间**另立标记键。

**三、"一次性"是作者的事，引擎只登记**

- 引擎**不做任何"只判定一次 / 只出现一次"的拦截**：它只把"这套方案执行完了"这个**事实**写进池。
- 是"只判定一次""只出现一次"还是"每次都能聊"，**全部由作者**在该 mod 模板的 `conds` 里表达（§4.5）——引用或**不引用**这条记录键都行。
- 引擎与编辑器为此提供**「mod 一次性」判定模板**（预设），作者套用即可（§6.7 / §9.7）。

**四、写入与默认值的总口径**：`engine-roll.*` **只写"发生了的事"**（落地的 `npcId` / 执行完的 `true`），**绝不预建任何键** —— "没有发生的事情不建键"，读取一律走上方各自的缺省值。

## 四、读与写是两个维度

### 4.1 硬规则：读不写、写不读

**判定表达式只由读算子构成，修改动作只由写算子构成；两者不互相嵌套、不组成表达式树。**

- 池的接口分**读接口**（判定）与**写接口**（修改）两个，**对所有对象（NPC、建筑、回合判定）一律可用、一律可见**。**两者都按 `space` 参数化**（§2.5）：调用时给 `space ＋ 短名`，由接口拼出规范全名。
- **写接口不提供读反馈**：写算子没有返回值、不参与任何判断。因此 **`if (set("usr-aaa", true)) { … }` 这种写法在设计上不存在**，也不会被编辑器产出。
- 需要"先写、再按新值判断"时，写成**两条**：先一条修改、再一条判定（判定读的是写完之后的当次值）。

### 4.2 读算子（判定用）

| 算子 | 适用类型 | 含义 |
|---|---|---|
| `equals` | `string` / `number` / `boolean` | 等于 |
| `notEquals` | `string` / `number` / `boolean` | 不等于 |
| `greater` | `number` | 大于 |
| `less` | `number` | 小于 |
| `greaterEqual` | `number` | 大于或等于 |
| `lessEqual` | `number` | 小于或等于 |
| `contain` | `string` | 包含子串 |
| `notContain` | `string` | 不包含子串 |

- 读算子**不含任何写算子**（§4.1）。
- 数值比较为**精确比较**，不设容差。
- `contain` 区分大小写与全半角。
- **值可以是字面量，也可以是另一个池键的引用**（**键对键比较**，**裁决 58**）：条件项写成 `{ name: usr-a, op: greater, ref: usr-b }`——`ref` 表示"右侧取该键的**当前值**"（即 `a > b`）。**两侧类型必须一致**（不一致出 `K26`）；`ref` 指向的键**必须已声明**（否则 `K20`）；`ref` 与字面量 `value` **二选一**，同时写则只认 `ref` 并提示。

### 4.3 写算子（修改用）

| 算子 | 适用类型 | 含义 |
|---|---|---|
| `set` | `string` / `number` / `boolean` | 赋为给定值 |
| `append` | `string` | 在末尾追加给定文本 |
| `add` | `number` | 加上给定数值 |
| `minus` | `number` | 减去给定数值 |
| `multiply` | `number` | 乘以给定数值 |
| `divide` | `number` | 除以给定数值（除数为 `0` 时**拒绝执行**并出 `K22`） |
| `toggle` | `boolean` | 取反后重新赋值（`true` → `false`，`false` → `true`） |

- 写算子的值一律是**字面量**（按声明类型解释），**不是**另一个池变量，也**不是**表达式。
- 每条修改**只作用于一个键**；要改多个键就写多条。

### 4.4 判定的组合

一次判定可以由**多条读算子**组成，以 `mode` 决定合取方式（沿用门锁 `Gate.mode` 的既有口径）：

| `mode` | 含义 |
|---|---|
| `all`（缺省） | 全部条件成立才算成立 |
| `any` | 任一条件成立即算成立 |

- 空的判定集合**视为成立**（无用例），并在编辑器标黄提示"这条判定没有任何条件"。
- **读算子的值可以是字面量，也可以是另一个池键的引用**（`ref`，§4.2）——键对键比较**已开放**（裁决 58）。
- **判定可以起名复用**：把条件写成一个**判定模板**后，使用处只写模板名（§4.5）。

### 4.5 判定模板（命名条件）

**一段条件可以起名，成为"模板"，供任意使用处引用**——这是"同一条条件在多处复用"的手段（**裁决 53**）。

**它本质是"判定的函数"**：一段可命名的条件，**可以用在所有能使用判定的地方**（对话 `if` / `pool`、门锁 `pool`、建筑触发前置、**回合判定的 `when`**……），使用处只写模板名。

**与回合判定天生可嵌套**：模板是**纯条件、随处即时求值**；回合判定（`checks`）是**带动作的定时执行**。回合判定的条件栏可直接引用一个模板——伪代码即 `RoundCheck: A = if (CondTpl) { hp + 1 }`（判定 `A` 的条件取模板 `CondTpl`、动作写 `hp + 1`）。

**模板属于作者素材（预设库）的一部分**：与组件一样可**自建**、可把常用判定沉淀为预设；模板库是"待用的工具"，**本局用到哪些就随 `.pmod` 带走**。使用处条件栏的「转存为模板」即把内联条件沉淀进库（§9.7）。

**声明**：写在 `.pmod` 的 `## Pool` 段，与变量声明并列（§7.1）：

```yaml
## Pool

conds:
  - { key: bag_full, desc: 背包已满, when: { mode: all, items: [ { name: engine-inventoryUsed, op: greaterEqual, value: 10 } ] } }
  - { key: rich,     desc: 手头宽裕, when: { mode: any,  items: [ { name: engine-item.gold, op: greaterEqual, value: 100 },
                                                          { name: engine-item.gem,  op: greaterEqual, value: 5 } ] } }
```

**引用**：使用处的 `if` / `pool` 判定位置，可以直接写**模板名**代替条件体：

```yaml
- if: bag_full
  message: ["你的包袱已经装不下了。"]
  pool: [ { name: usr-tried_open, op: set, value: true } ]
```

对应关系（两处）：`{ key, when }` 声明 → `if: <模板名>` 引用。

| 规则 | 说明 |
|---|---|
| **模板只含条件、不含动作** | 模板是"命名条件"（`when`），**没有 `pool` 动作**。要"条件 ＋ 效果"一起按回合复用，那是**回合判定**（`checks` 的 `alias`，§6.2），两者分工不同。 |
| **不支持模板引用模板** | 模板的 `when` 里可引用变量与字面量；引用另一个模板**不开放**（避免成环与查错困难）——需要时把两条条件用 `mode: all` 并列写上。**注意方向**：模板不可引用模板，但**回合判定可以引用模板**（`RoundCheck` 的 `when` 取模板名，见上"天生可嵌套"）。 |
| **模板名只落在作者空间** | 与变量一样按 §2.2 补 `usr-`；与**变量同名**即出 `K36`。 |
| **引用未声明的模板** | 出 `K35`：该处条件**恒不成立**（运行时按"未成立"处理），编辑器提供"补一条模板"快捷操作。 |
| **不绕过写权限** | 模板内部写法与普通判定完全一致（§4.2）；用模板引用引擎键**不会**变成可写（模板只读，§3.5）。 |

**为什么另起一套**：回合判定的别名是**带动作的定时执行**（每回合跑一次）；模板是**纯条件、随处即时求值**。宝箱要"开箱那一刻按背包是否满走不同分支"，用模板即可，不必等回合。两者是**嵌套**关系而非竞争——回合判定的条件栏可直接取一个模板（`RoundCheck: A = if (CondTpl) { … }`）。

## 五、判定：回合判定与触发判定

### 5.1 总则

**所有操作都依赖状态池的判定。**判定按**触发时机**分两类，**共用同一套读 / 写算子**（§四），只是**声明处**与**求值时机**不同：

| 判定 | 求值时机 | 声明处 | 典型用途 |
|---|---|---|---|
| **回合判定** | **每回合开始时**，整批求值一次 | `.pmod` 的 `## Pool`（`checks`）**＋ 引擎内置 ＋ `Rules.state` 派生**（§5.2 的"来源"） | 中毒每回合掉血、增益倒计时、地形 `cost`、步数计时、**存活 / 死亡判定**…… |
| **触发判定** | 事件触发的那一下 | 使用处**就地内联**（条件可内联，也可写**判定模板名**，§4.5） | NPC 对话分支、建筑触发、门锁放行、事件判定 |

### 5.2 回合判定

**回合判定每回合开始时整批求值一次。它不是"另起一段流程"，而是"来源不同的回合判定"按固定规则自然排序后的执行序列**——**基础判定、游戏业务判定、buff 判定本质上都是回合判定**，只是**登记方不同**。

**三个来源**（内部字段 `source`，作者不填、不落 `.pmod`）：

| 来源 | 登记方 | 内容 | 排序批次 |
|---|---|---|---|
| `pmod` | 作者 | `## Pool` 的 `checks` 里声明的**游戏业务判定** | 第 ① 批 |
| `state` | 引擎（由 `Rules.state` 派生） | buff / debuff 的每回合效果（`per_turn` 增减、`duration -= 1`） | 第 ② 批 |
| `engine` | 引擎内置 | **基础判定**：**存活 / 死亡判定**等 | 第 ③ 批（**强制最后**） |

- **基础判定强制最后**：**引擎内置的基础判定一律排在游戏业务判定与 buff 判定之后**——这样"扣血 / 补血 / buff 结算"全都发生后，**最后才判死**，避免"先扣血死掉、后自动补血"的 bug。**角色死亡本身就是一条内置回合判定**，因此**不存在"存活判定 → 回合判定批 → 状态 tick"三段流程**，只有**一批回合判定按来源自然排序**。
- **批内再排序**：同一来源内部按 §8.4 的拓扑排序 ＋ 匿名后置排定。
- **允许前置操作依赖**（`deps`）：一条回合判定可声明它必须排在**另一条（或多条）回合判定之后**执行——这解决"先算 A 再算 B，算反了结果就不同"的问题（buff / debuff 的先后、先扣血再判死等）。
- **依赖可多条**：`deps` 是数组，一次可写**多条**前置；**每一条都是排序约束**，本判定排在全部前置之后。
- **依赖必须指名到"别名"**：**只有为一条判定创建了别名（`alias`），别的判定才能依赖它**；没有别名 ＝ 不可被依赖。
- **前置依赖缺失即跳过，不影响本条**：`deps` 里的别名**不存在**（或对方**没有别名**）时，**只忽略这一条依赖、本判定照常执行**，并出 `K28` / `K31` 提示（§十）；**绝不因为前置缺失而跳过本判定**。
- **运行时用拓扑排序排列批内顺序**（§8.4）：
  - 有名判定（有 `alias`）之间按依赖关系 **拓扑排序**；
  - **匿名判定（无 `alias`）永远排在有名的之后**，彼此保持**声明顺序**。
- **禁止回环**：依赖关系一旦成环（A → B → A），编辑器**在编辑页面警告并禁止保存/导出该依赖**（§10 `K30`）。运行时遇到（手写文件）则以**声明顺序**兜底执行、不卡死。

### 5.3 触发判定

- **在事件触发的那一下求值**：进入建筑、踩到道路格、打开某个 NPC 的对话、走到某条对话记录……凡是"使用处"，其条件即触发判定。
- **就地内联**，不集中声明：NPC 用对话树的 `if` / `pool`（§6.3），门锁 `Gate` 用 `pool`（§6.4），建筑触发用其 `encounter` 前置的判定。
- 触发判定**没有别名、不参与拓扑排序**（那是回合判定专有）；它随使用处的求值顺序自然发生（§8.3）。
- **条件可以内联，也可以引用模板**：`if` / `pool` 位置既可写条件体，也可写**判定模板名**（§4.5）；两者在运行期等价。

### 5.4 两种判定的共用结构

两者共用同一对字段形状（写法与 NPC 对话树一致）：

- **条件** `{ mode?, items: { name, op, value }[] }` —— `op` 为读算子（§4.2）；`value` 为字面量，或改写为 `ref: <另一池键>` 做**键对键比较**（§4.2，裁决 58）。**条件体也可整体替换为一个判定模板名**（§4.5）。
- **动作** `{ name, op, value }[]` —— `op` 为写算子（§4.3）。

唯一的差别是：**回合判定多一组元字段"来源 / 别名 / 依赖"**（§6.2），触发判定没有。

## 六、数据模型

### 6.1 声明项 `PoolVar` 与判定模板项 `CondTpl`

`.pmod` 的 `## Pool` 段有**两组声明**：变量（`pool`）与**判定模板**（`conds`，§4.5）。以下先列**变量项**：

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `key` | `string` | **必填** | **短名**（不含空间词）。落盘时由解析器按 §2.2 补成规范全名并写入 `name` |
| `name` | `string` | 落盘必填 | **规范全名**（`usr-<短名>`）。导入时若只给了 `key` 则按 §2.4 补齐 |
| `type` | `'string' \| 'number' \| 'boolean'` | **必填** | 声明类型 |
| `value` | 依 `type` | **必填** | 默认值（初值） |
| `desc` | `string` | 可省 | 说明文本（编辑器表格的"说明"列，供作者自查） |

- **`引用数` 不是字段**：它是编辑器按当前工程统计出来的**派生列**（§9.2），不落盘、不进 `.pmod`。
- 同一份 `.pmod` 内**同 `name` 只允许出现一次**；重复即出 `K21`，取**先出现的那一条**。

**判定模板项**（`conds` 的数组元素，语义见 §4.5）：

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `key` | `string` | **必填** | **短名**（不含空间词）；落盘时补成 `usr-<短名>` |
| `name` | `string` | 落盘必填 | **规范全名**（`usr-<短名>`） |
| `desc` | `string` | 可省 | 说明文本（编辑器表格的"说明"列） |
| `when` | 判定 | **必填** | 模板条件（读算子，§5.4） |

- 模板项**没有 `type` / `value`**——它不是一个值，只是一段可命名的条件。
- **模板名唯一**：同 `## Pool` 内重复即 `K21`；**与变量同名即 `K36`**（两者的短名共用一个命名空间）。

### 6.2 回合判定项 `RoundCheck`

`.pmod` 的 `## Pool` 段里另有一组 `checks`，是**回合判定**的数组：

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `alias` | `string` | 可省 | **别名**：给这条判定命名。**只有起了别名，别的判定才能依赖它**；不写 ＝ 匿名判定 |
| `deps` | `string[]` | 可省 | **前置依赖**：本判定排在所列**别名**对应的判定之后执行。**可写多条**；只能填别名 |
| `when` | 判定 | **必填** | 触发条件（读算子，§5.4） |
| `pool` | 修改动作[] | **必填** | 条件成立时执行的修改（写算子，§5.4） |

- **`source` 不是 `.pmod` 字段**（§5.2）：它是运行期为每条回合判定标注的**来源**（`pmod` / `state` / `engine`），由登记方决定，用于"先业务与 buff、后基础判定"的自然排序；作者写不进、改不了。
- **`deps` 可多条**：数组里每一条都是一份排序约束，本判定排在**全部**前置之后。
- **前置缺失即跳过该依赖**：`deps` 指向**不存在 / 无别名**的判定 → 只忽略**这一条依赖**（出 `K28` / `K31`，§十），**本判定照常执行**。
- **别名在 `checks` 内全局唯一**：重复即 `K29`。
- **依赖成环即 `K30`**：编辑器标红并**不允许保存/导出**该依赖（§九 / §十）。
- 条件不成立的回合判定**不执行其 `pool`**，也**不算作一次"前置操作"**——但依赖它的判定**照常执行**（依赖表达的是"排序关系"，不是"成功条件"；要"A 成了才执行 B"，请把 A 的结果写进池、由 B 的 `when` 去读）。

### 6.3 对话树接入（NPC）— if-else 条件判断

对话树沿用**全树同一个结构**（[`02-data-model.md`](02-data-model.md) §4.9.2）；在既有字段上**新增两项**：

| 新增字段 | 类型 | 含义 |
|---|---|---|
| `if` | 判定 **或 `string`** | **条件**：本条记录是否进入候选。写条件体，或写一个**判定模板名**（`string`，§4.5）。同一层数组里的多条 `if` 组成 **if-else 链**（见下） |
| `pool` | 修改动作[] | **修改状态池**：本条记录说完之后的操作结果，与 `give` 同级并列（先结算 `give`，再执行 `pool`） |

**同层数组的求值方式（三选一，由本层出现的结构性字段决定）**：

| 本层情况 | 求值方式 |
|---|---|
| **完全不含 `if`**（且不含 `dice`） | **顺序展示**：自第一条起**逐条推进**（沿用 V2.0 口径，根层数组常只写一条） |
| **含任意 `if`** | **if-else 链**：按声明顺序找**第一条 `if` 成立**的记录 → **选中它、本层立即停止**（不再看后面） |
| **含 `dice`** | **随机选择**：沿用既有 `dice` / `hit` 口径（§4.9.2），在本层记录里按点数命中一条 |

**if-else 链的规则（这是 `if` 的完整语义）**：

1. 自本层第一条起，自上而下看；
2. **第一条 `if` 成立的记录被选中并展示**，此后**本层停止**——这就是 `else` 的排他性；
3. **一条不写 `if` 的记录 ＝ `else`**：仅当它**之前的所有 `if` 记录都不成立**时才被选中。作者通常把它放在本层末尾；
4. 若本层**所有 `if` 都不成立、且末尾没有"无 `if` 记录"**，则**本层结束**（＝隐含空 `else`）；
5. 被选中记录自己的 `items` 递归套用本规则 → **这就是嵌套**。嵌套**不设深度上限**（由编辑器与机器承受力兜底）。

**同层混用即提示**：一层里同时出现 `if` 与 `dice`（或 `hit`）时出 `K33`（§十）；运行时**以 `if` 优先**（骰子被忽略）。

- `pool` 的元素形如 `{ name, op, value }`：`name` 为规范全名，`op` 为写算子（§4.3）。
- `if` 形如 `{ mode?, items: { name, op, value }[] }`：`op` 为读算子（§4.2）。
- **`if` 与 `dice` / `hit` 正交**：`if` 管"哪些记录进入候选"，`dice` / `hit` 管"在候选里选中哪一条"。若层内既有 `if` 又有 `dice`，**先按 if-else 链筛出候选，再按骰子在该批候选里选**；若筛完**一条不剩**，视为**本层结束**（不再要求掷骰）。
- **根层记录的 `if` 同样生效**：根层若含 `if`，即按 if-else 链求值（与深层一致）。
- **`when` 的兼容**：上一版拟用的"逐条过滤 `when`"**并入本结构**——手写文件里若出现 `when: X`，读作"单分支的 `if`"（`当且仅当 X 成立时该条进入候选`）。**编辑器只产出 `if`，不再产出 `when`**。写在**内容**里，不是前置配置。
- **`if` 可写模板名**：`if: bag_full` 与把该模板的 `when` 原样内联**等价**（§4.5）。
- **一次性对话不再是引擎内建分支**：改由"标记 ＋ `if` / 模板"表达，见 §6.7（裁决 54）。

### 6.4 建筑与门锁接入

**门锁 `Gate`**（[`02-data-model.md`](02-data-model.md) §4.4 / §4.5）在既有 `tags` / `mode` / `missing` / `penalty` 上**新增一项**：

| 新增字段 | 类型 | 含义 |
|---|---|---|
| `pool` | 判定 **或 `string`** | **触发判定**：与 `tags` **同档并列**，两者**都**要满足才放行；`mode` 沿用门锁既有的合取口径。可写条件体，也可写**判定模板名**（§4.5） |

- 落点即门锁的既有落点（道路节点与建筑实例），**不新增使用位置**。"道德过低无法进入寺庙"即由建筑实例的门锁 `pool` 表达。
- **建筑触发判定**：建筑的 `encounter` 行为前置也可以带一条 `pool` 判定（与门锁同构），用于"到访即触发"的反馈切换。
- **建筑的状态反馈切换**：**不再额外记录**（**裁决 56**）——建筑（含宝箱房）按状态走不同反馈，一律由 **`pool` 判定 ＋ 判定模板 ＋ 对话树 `if`** 表达（即 §6.7 的方案），不新增机制、不新增内置键。

### 6.5 观察登记 `watch`

- **使用处登记它关心的池键**，使键一变，该使用处的**触发判定**即可按新值重算——这就是"NPC 注册观察"的机制。
- **`watch` 是派生字段，不落盘**：**自动由该使用处的全部 `if` / `pool` 引用键推导**（去重），作者**不需要手写**。
- 运行时维护 **`键 → 登记了该键的使用处` 反查表**（§8.5）。池键被写入时，对照本表把相关使用处标记为**需重算**。
- **典型场景（道具件数）**：NPC 写 `if: { name: engine-item.apple, op: greaterEqual, value: 3 }`，即等于"注册观察苹果数量"——玩家凑齐 3 个苹果后，该 NPC 的该分支即可切换（§3.4）。
- **玩家不可见**（**裁决 59**）：`watch` 是**作者维度的事件触发机制**——只用于"键一改、正在展示的使用处按新值重算"，**不向玩家暴露任何提示 / 列表**（不做"像任务提示那样"的可见 UI）。

### 6.6 编辑器内部形态

编辑器内部以**一张表**持有全部声明（§9.2）；使用处只持有**规范全名 ＋ 算子**，不回写声明表（**自动收录**是唯一的例外，§9.4）。

### 6.7 预设判定：一次性对话

**引擎不判断"某段对话只说一次"**（原 `retalk` 开关、交付终态、进度标记一律退役，见 §十一）——同一件事改由**引擎记录 ＋ 池判定**表达（**裁决 61**；数据形态**修订裁决 54**）。引擎只做一件事：**这套方案执行完就写 `engine-roll.mod.*`**（§3.6）。"要不要只说一次"由作者用**判定模板 ＋ `if`** 决定。NPC 场景下，作者有两条路：

| 选择 | 作者做什么 | 效果 |
|---|---|---|
| **套用「一次性对话」** | 在 NPC 上勾选预设（编辑器按当前使用处自动挂上**引擎提供的「mod 一次性」判定模板** ＋ 一条首层 `if`） | 该段内容**只在首次进入时展示** |
| **自定义** | 自己用 `pool` 写标记、用 `if` / 模板判标记 | 完全自由的组织方式（如"换一批台词"而不是"不再说"） |

**「套用」的落地形态**（按此生成，作者可改；实例 key / `npcId` / `modId` 三段在勾选时按当前使用处填实）：

```yaml
## Pool

conds:
  # 引擎提供的预设判定模板：这一位 NPC 的这一套方案尚未执行过
  - key: mod_first_time
    desc: 该实例的该 NPC 的该方案尚未执行过
    when: { mode: all, items: [ { name: "engine-roll.mod.<建筑实例 key>.<npcId>.<modId>", op: equals, value: false } ] }
```

```yaml
### NPCs
- id: n_elder
  dialogs:
    Mod1:
      - if: mod_first_time
        message: ["年轻人，我等你好久了。"]
        give: [red_potion]
      - message: ["……"]        # else：已经聊过了
```

- **判据是引擎的记录，不是作者写的标记**：`engine-roll.mod.*` 由引擎在**这套方案执行完**时写为 `true`（§3.6）；未执行过时**键不存在**，读取得 `false` —— 模板判的正是这个 `false`。
- **模板按使用处生成**：每个"要一次性的方案"各有一条具体模板（条件里的三段填实成它自己），作者可改名、可改条件；与变量**共用命名空间**，重名按 `K36` 提示（§4.5）。
- **勾选预设只做两件事**：挂一条模板 ＋ 写首层 `if`（要防刷就把带 `give` 的记录一并包进同一条 `if`）。**不再写任何作者空间标记键**（**裁决 61** 对裁决 54 的修订点）。
- **引擎不再为对话进度单独记账**，故存档里只有池（§8.6）。
- **不再有"重入菜单 / 重新对话 / 交付终态"的内建分支**：要"可以重聊"就**什么都不做**（不引用模板即可，引擎照常执行、照常写记录）；要"换成别的话"就把 `else` 分支写成新内容——组织方式全交给作者。
- **建筑同理**（**裁决 56**）：宝箱房"开过就不再开"＝ 同一模式（引擎记录 ＋ 模板 ＋ `if`），不新增机制。

## 七、`.pmod` 段的声明与引用

### 7.1 顶级段 `## Pool`

状态池是**独立的顶级段**，与 `Background` / `Components` / `Rules` / `Maps` 并列，**声明全部池变量的默认状态与定义**、**判定模板（`conds`）**，**并集中声明回合判定**：

```yaml
## Pool

pool:
  - { key: morality, type: number, value: 50, desc: 道德；盗窃与施舍会影响它 }
  - { key: met_merchant, type: boolean, value: false, desc: 是否已经见过那位商人 }
  - { key: merchant_price, type: number, value: 100, desc: 商人当前报价 }
  - { key: poisoned, type: boolean, value: false, desc: 是否中毒 }

# 判定模板（命名条件，可被任意使用处引用，见 §4.5）
conds:
  - { key: bag_full, desc: 背包已满, when: { mode: all, items: [ { name: engine-inventoryUsed, op: greaterEqual, value: 10 } ] } }

# 回合判定（每回合开始执行一次，见 §五 / §八）
checks:
  - alias: poison_tick                       # 起名 → 可被依赖
    when: { mode: all, items: [ { name: usr-poisoned, op: equals, value: true } ] }
    pool: [ { name: engine-hpValue, op: minus, value: 1 } ]
  - alias: price_drift
    deps: [ poison_tick ]                     # 前置依赖：排在 poison_tick 之后
    when: { mode: all, items: [ { name: usr-met_merchant, op: equals, value: true } ] }
    pool: [ { name: usr-merchant_price, op: add, value: 1 } ]
  - when: { mode: all, items: [ { name: usr-morality, op: less, value: 20 } ] }   # 匿名判定：永远最后
    pool: [ { name: usr-met_merchant, op: set, value: false } ]
```

- **段标题一律英文 `Pool`**（与其余顶级段同一约定，[`01-pmod.md`](01-pmod.md) §3.1）；解析时**先匹配英文、未命中再降级中文**（同一约定）。
- **`pool` / `conds` / `checks` 都是可省的**：缺任一 ＝ 该组为空，均不报警。
- **缺该段 ＝ 空声明 ＋ 无模板 ＋ 无回合判定**：此时任何 `usr-` 引用都会出 `K20`。
- **引擎空间的键不出现在本段**（§2.2）；引擎键的权威清单是 §三 总表。

### 7.2 使用处内联

使用处**不重复声明**，只在原地写"读什么 / 写什么"，**和 NPC 对话树的写法一致**（把条件与操作内联在使用的节点上）：

```yaml
### Buildings
- id: b_temple
  name: 神庙
  ...
  # 门锁（触发判定）：道德低于 30 不放行
  gate: { mode: all, pool: { mode: all, items: [ { name: usr-morality, op: greaterEqual, value: 30 } ] } }
  # 也支持：直接写判定模板名（§4.5）—— gate: { mode: all, pool: rich }
  # 也支持：键对键比较（§4.2）—— pool: { mode: all, items: [ { name: usr-morality, op: greaterEqual, ref: usr-merchant_price } ] }
```

```yaml
### NPCs
- id: n_merchant
  name: 商人
  dialogs:
    Mod1:
      # 根层含 if → 按 if-else 链求值（命中一条即停）
      - if: { mode: all, items: [ { name: usr-met_merchant, op: equals, value: true } ] }
        message: ["又见面了。"]
        pool: [ { name: usr-merchant_price, op: add, value: 20 } ]
        items:
          # 嵌套：凑齐 3 个苹果才给货
          - if: { mode: all, items: [ { name: engine-item.apple, op: greaterEqual, value: 3 } ] }
            message: ["三个苹果，成交。"]
            give: [red_potion]
          - message: ["苹果不够，别耽误我做生意。"]      # else（本层末尾的无 if 记录）
      - message: ["没见过你。"]                          # 根层的 else
        pool: [ { name: usr-met_merchant, op: set, value: true } ]
```

### 7.3 兼容与容错

| 情形 | 处理 |
|---|---|
| 老 `.pmod`（无 `## Pool` 段、无 `if` / `pool` 字段） | **正常读取**：声明为空、使用处无判定与修改 —— 与 V2.0 行为完全一致 |
| 手写 `when`（旧拟用法） | 读作"单分支的 `if`"（§6.3 末）；导出时统一改写为 `if` |
| 声明项缺 `type` / `value` | 取该类型的零值（`''` / `0` / `false`）并提示一句 |
| 声明项 `value` 与 `type` 不符 | 按 `type` 解释后取零值，并出 `K24` |
| 使用处引用了未声明的 `usr-` 键 | **不拦截**（可能是先写引用、后补声明）；出 `K20` 并在编辑器提供"补一条声明"的快捷操作 |
| `checks` 的 `deps` 指向不存在的别名 | 出 `K28`；该依赖**不成边、被忽略**，本条按"无此前置"参与排序并**照常执行** |
| `checks` 依赖成环 | 出 `K30`；编辑器**不允许保存 / 导出**，手写文件按声明顺序兜底 |

## 八、运行时

### 8.1 持有形态

- 池是**一局一份的纯数据对象**：`Record<规范全名, string | number | boolean>`。
- **`engine-` 与 `usr-` 在同一个对象里**，靠前缀区分空间；不分成两个容器。
- 另有两张**派生结构**（不落盘）：**声明登记表**（§2.5）与**观察反查表**（§8.5）。
- **存储不分空间**：接口层的 `space` 参数只在调用时拼前缀（§2.5），池本身没有"分区"概念。

### 8.2 开局播种

1. **先播种引擎空间**：
   - 按主人公职业的 `base_stats` 与玩家的分配点算出六维与上限（`hpValue` / `hpMax` / `mpValue` / `mpMax` / 四能力），`hpValue` / `mpValue` 取满值；
   - 写入 §3.2 的其余引擎键，其中 **`engine-steps` 置 `0`**、**`engine-pos` 置起点串**、`engine-round` 置初始回合；
   - 按职业的 `starting_items` 汇总 **`engine-item.<道具 id>`**（未持有者不建键，读取按 §3.4 缺省 `0`）。
2. **再播种作者空间**：按 `.pmod` 的 `## Pool` 的 `pool` 声明逐条写入 `value`。
3. **装载回合判定**：汇总本回合的**全部来源**（① 作者 `checks`；② 由 `Rules.state` 派生的 buff / debuff 效果；③ 引擎内置基础判定），**按 §8.4 排定执行序列**，存为当次运行的执行列表。
4. **播种是覆盖式的**：`usr-` 与 `engine-` 空间不重叠（§2.1），故两次播种互不影响。
5. 播种完成后**构建声明登记表**（§2.5）与**观察反查表**（§8.5）。

### 8.3 求值顺序

**回合开始时序 —— 不是三段流程，而是"一批回合判定按来源自然排序"：**

| 批次 | 来源 | 内容 |
|---|---|---|
| ① | `pmod` | 作者 `checks` 里的**游戏业务判定**（批内按 §8.4 排序） |
| ② | `state` | `Rules.state` 的 **buff / debuff 每回合效果**（`per_turn` 增减、`duration -= 1`） |
| ③ | `engine` | **引擎内置基础判定：存活 / 死亡判定**等（**强制最后**） |

- **三批顺序拼接、逐批执行**：① → ② → ③；每批内部按 §8.4 排定（有名拓扑、匿名后置）。
- **基础判定强制最后**：先让业务与 buff 把 HP 增减算完，**最后才判死**——这消除了"先扣血死掉、后自动补血"的 bug。**旧口径的"存活判定第一"由此作废**（`SP-11` 收口，非冲突）；`engine` 批次与 [`03-engine.md`](03-engine.md) §4.8.0 的衔接见 §十一。
- **没有独立的"存活判定步"、也没有独立的"状态 tick 步"**：存活 / 死亡是 `engine` 批次里的一条回合判定，buff tick 是 `state` 批次的内容——**它们只是来源不同**。
- **缓冲立场（`SP-11` 收口）**：基础判定排到最后 → 玩家 `hp` 若在**本回合结算里**降到 `0`，**本回合开始即判死**；但**"吃药"是回合内自由动作（不占回合、不推进时间、不 tick）**，可在**任何一回合内随时**使用。于是缓冲不再是"先判血后 tick"的顺序，而是 **"本回合吃药 → 次回合 `state` tick 里回血与掉血累加对冲 → `engine` 判定时 `hp` 仍 > 0"**——**上个回合吃过药，下个回合就死不掉**。旧口径"给一回合缓冲吃药"的**意图不变**，只是缓冲的落点从顺序改成了**玩家的一次自由动作 ＋ buff 对冲**。

**其余场合（触发判定）：**

| 场合 | 顺序 |
|---|---|
| 进入建筑 | ① 门锁 `pool` 判定 → ② NPC 触发（对话内逐层 `if` 判定与 `pool` 执行） → ③ 建筑的 `encounter` 行为 |
| 踩到道路格 | 门锁 `pool` 判定排在既有 `tags` 判定之后、`missing` / `penalty` 结算之前 |
| 对话内一层 | ① 按本层求值方式（顺序 / if-else 链 / 骰子，§6.3）选出记录 → ② 展示 `message` → ③ 结算 `give` → ④ 执行 `pool` → ⑤ 处理 `items`（递归进下一层） |

- 修改动作**立即生效**（同一帧内后续读取就能读到新值），因此"先写、再判"的写法（§4.1）在**同一层**里即可完成。
- 判定与修改**不产生任何提示浮条**：它们是状态变化，不是财物交割；玩家可见的反馈由作者的文案（`message`）与后续 `if` 分支承担。

### 8.4 回合判定的排序（拓扑排序）

**求值序列 ＝ "先按来源分批，再在批内做拓扑排序"：**

1. **分来源分批**：把本回合的**全部**回合判定按 `source` 归入三批——`pmod` → `state` → `engine`（§5.2 / §8.3）。
2. **逐批排定**（对每一批重复 a–e）：
   - a. **建图**：取该批里**有 `alias`** 的判定，按 `deps` 建有向边（`deps` 里的别名 → 本条）。
   - b. **拓扑排序（稳定）**：用 **Kahn 算法**，入度为 `0` 的节点**按声明顺序**出队 —— 这保证"没有依赖关系的判定之间**保持作者写下的顺序**"，排序结果稳定可复现。
   - c. **匿名后置**：**匿名判定（无 `alias`）不参与拓扑排序**，一律**按声明顺序追加在本批全部有名判定之后**。
   - d. **回环兜底**：若建图后**仍有剩余节点**（即成环，`K30`）→ **按声明顺序**把这些节点接在本批末尾执行（不卡死、不丢判定）。
   - e. **缺依赖忽略**：`deps` 指向的别名**不存在 / 无别名** → **该条依赖不成边**，**不影响本条判定的排定与执行**（§6.2）。
3. **拼接**：三批顺序拼接（`pmod` → `state` → `engine`）即为最终执行序列。
4. **执行**：按排定序列逐条求值——`when` 成立才执行其 `pool`。

> **为什么分"有名 / 匿名"**：依赖只能指向**有名字**的东西（否则无处指认）。把匿名判定统一放到最后（**批内**），就等于默认"匿名判定是**纯副作用**、不承担前置职责"，避免作者在没起名的判定上"偷偷挂依赖"而在编辑器里查无此名。

> **典型用法（buff / debuff）**：`poison_tick` 是作者（`pmod`）判定，`death_check` 是引擎内置（`engine`）判定——**前者天然排在后者之前，作者无需显式挂依赖**；批内的先后（如"先加攻再算伤害"）才用同批别名串起来。

### 8.5 触发判定与观察

- **触发判定的求值时机是"使用处被触发的那一下"**（进入建筑、踩格、进入某层对话……），与 `engine-round` 的推进无关。
- **观察反查表**：启动时按每个使用处的**派生 `watch`**（§6.5）建立 `键 → 使用处集合` 的反查表。
- **写入即通知**：任何一次写算子落到某键上，引擎查反查表，把登记了该键的使用处标为**需重算**：
  - 该使用处**当前未在展示** → 无需动作（下次被触发时自然按新值求值）；
  - 该使用处**正在展示**（如对话进行中） → **即时重算**当前层（例如玩家在对话中恰好凑齐道具，则当前层的 if-else 链按新值重选）。
- **不产生浮条**（同 §8.3）。

### 8.6 存档

- **`psave` ＝ 状态表**（**裁决 55**）：一局的**全部运行期可变状态**都落在池上（引擎空间 ＋ 作者空间），存档即保存整张池——**池之外不再有第二份可变状态**。落点：**抽定的 NPC / 方案**＝ `engine-roll.npc.*` / `engine-roll.mod.*`（§3.6，**裁决 61**）、**一次性对话的判据**＝引擎的执行记录（＋作者自己的标记，若要）、**`once` 已用掉的建筑 / 格子**＝ 池键（§十一）。
- **验收口径**：读档后重建出的运行态与存档前**逐键相等**；任何"只存在别处、没进池"的状态字段都视为**迁移未完成**。
- 池是纯数据（三类型字面量），**无序列化特殊处理**；读档即整体替换。
- **派生结构不落盘**：声明登记表与观察反查表在**读档后按"引擎键 ＋ 当次声明"重建**。
- 老 `.psave` **不做迁移**（本引擎无存量用户）：版本号不匹配即按既有规则拒载，由既有机制提示。

## 九、编辑器设计

### 9.1 入口与面板

- **入口在编辑模式的工具栏**，与「NPC 模组」同级。
- 点击后**单独弹出一个对话框面板**（与 NPC 模组面板同一形态），**不占画布模式条**（沿用 G7 的口径）。
- 面板归属于**当前工程**：池的声明与回合判定列表是这一局的内容，随工程持久化与撤销（新字段须同步登记持久化与撤销两处，[`00c-guidelines.md`](00c-guidelines.md)）。
- 面板分**三个页签**：「变量表」（§9.2）、「判定模板」（§9.7）与「回合判定」（§9.5）。

### 9.2 变量表格

面板主体是**一张表**，**引擎变量与作者变量同表展示**：

| 列 | 内容 | 可编辑 |
|---|---|---|
| `key` | **规范全名**（作者行为 `usr-<短名>`、引擎行为 `engine-<短名>`） | 作者行：是（只填短名，重名即提示）；**引擎行：否** |
| 说明 | `desc` 文本 | 作者行：是；**引擎行：否**（引擎自带说明） |
| 类型 | `string` / `number` / `boolean` 三选一 | 作者行：是（改类型须同时校正默认值）；**引擎行：否** |
| 引用数 | 当前工程里引用该键的**处数**（派生统计，§6.1） | 否 |
| **空间** | **`引擎` / `作者` 标记（tag）** | 否 |

- **「引擎」tag 的来源**：以 §三 总表为清单**逐行列出全部内置变量**，一律打 **`引擎`** tag、**只读**（作者不可改短名 / 类型 / 初值）；作者行打 `作者` tag、可编辑。
- **筛选与搜索**：表格提供"只看作者 / 只看引擎 / 全部"的筛选，以及按短名 / 说明的关键词搜索——这就是要求里"内置变量清单在表格中展示"的落点。
- 支持**添加**与**删除**（仅作者行）。删除一个**仍有引用**的键时，提示引用处数并要求确认（不自动清理引用；引用处此后出 `K20`）。

### 9.3 自动推荐

- 在**对象设置面板**里输入关键词时，**变量名那一栏给出相关变量的推荐**（按前缀匹配短名与说明文本）。
- 推荐项**跨空间**：作者空间的键与**引擎空间的键一并列出**——**注册时可自动联想内置变量**（要求项）。引擎变量在推荐列表里同样带 `引擎` tag。
- **写引擎键时的空间提醒**（**裁决 51**）：在**写算子**（`pool` 动作）里选中一个 `engine-` 键时，该行固定显示提示"**这是引擎变量，写入会影响游戏流程**"，并标出它是否落在**可写四类**之内（§3.5）；不在可写范围内则同时标红（`K23`）。这是"**用户向的操作区分空间**"在编辑器侧的落点。
- 选中引擎空间的键时，该栏锁定为**只读选择**：不可改短名、**不可改类型**，并可即时提示该键的写权限（只读 / 可写，§3.5）。

### 9.4 自动收录

- 在变量名栏里输入一个**不存在的短名** → 标记为 **`new`**，并在保存该对象时**自动收录**进状态池，类型取该处算子的**适用范围推断**（读 `greater` → `number`；`contain` → `string`；`toggle` → `boolean`；无法推断时默认 `number`），默认值取该类型的零值。
- 收录**不留待确认**：与"先写引用、后补声明"的用法一致（§7.3）。类型推断有歧义时（如 `equals` 对三类型都成立）在面板里标黄提示，请作者到面板中确认。
- 自动收录**只进作者空间**（`usr-`）；引用 `engine-` 却不存在的名字**不收录**，只出 `K20`（引擎键只能由引擎建立）。

### 9.5 回合判定编辑器（「回合判定」页签）

- 列出 `checks` 的每一条，可填：**别名**（可空）、**依赖**（下拉多选**已有别名**）、**条件**（`when`）、**动作**（`pool`）。
- **依赖只列已有别名**：下拉里只出现其他条目的非空 `alias`——**从源头上杜绝"依赖一个没起名的判定"**（§8.4 的立场）。
- **分组展示（按来源分批）**：先按来源分 `pmod`（业务，作者可编辑）/ `state`（buff，只读派生）/ `engine`（内置基础判定，只读）三组；每组内有名判定按**拓扑排序后的执行序**排列并显示序号，匿名判定归入该组末尾的 **「匿名（批内最后）」** 区、不参与排序视图。**`engine` 组恒在最底部**（§8.3）。
- **回环警告（要求项）**：依赖图一旦成环，**在编辑页面高亮标红并给出环路路径**（`A → B → A`），并**禁止保存 / 导出**该依赖关系（§10 `K30`）。
- 提供"依赖图"小视图（节点 ＝ 判定，边 ＝ `deps`），便于作者核对先后。

### 9.6 对话 if-else 编辑器

- 对话树的每条卡片支持"+ 条件分支"，生成 **if / elseIf / else** 结构块；`else` 即"末尾的无 `if` 记录"。
- **嵌套**：任何分支体内可继续加"条件分支"，编辑器按缩进呈现层级。
- 同一层若已使用 `if`，**隐藏该层的 `dice` / `hit` 入口**（同层二选一，§6.3 / §10 `K33`）。

### 9.7 判定模板编辑器（「判定模板」页签）

- 列出 `conds` 的每一条：**短名**、**说明**、**条件**（`when` 的可视化编辑，与回合判定同一套控件）。
- **模板名与变量名共用命名空间**：起名时即时比对变量表，重名标红（`K36`）。
- **引用数**列：显示当前工程里有多少处 `if` / `pool` 引用了该模板；删除仍有引用的模板时提示处数并要求确认（引用处此后出 `K35`）。
- **不支持模板引用模板**（§4.5）：条件里只能引用变量与字面量；若引用了另一个模板名，标红提示改用 `mode: all` 并列条件。
- **本质是"判定的函数"，可用在所有判定位置**（对话 `if` / `pool`、门锁 `pool`、建筑触发前置、**回合判定的 `when`**）；**回合判定可直接引用模板**（`RoundCheck: A = if (CondTpl) { hp + 1 }`）。
- **模板属于作者素材（预设库）的一部分**：与组件一样可**自建**、可沉淀为预设；模板库只是"待用的工具"，**本局用到哪些就随 `.pmod` 带走**。
- 每个使用处的条件栏提供**"转存为模板"**：把内联条件收进模板并替换为模板名（同一条件在多处复用时省事）。
- **引擎提供一枚预设模板「mod 一次性」**（**裁决 61**）：条件即"当前方案的执行记录 `engine-roll.mod.*` 尚未为 `true`"（§3.6 / §6.7）。勾选 NPC 的「一次性对话」时按当前使用处**生成一条具体模板**（三段填实），之后可改名、可改条件——引擎**不新增字段、不做拦截**。

## 十、校验与提示（`K20` 起）

沿用既有口径：**只提示、不阻塞**保存与导出（**惟 `K30` 例外，见下**）。

| 编号 | 规则 | 违反时 |
|---|---|---|
| `K20` | 使用处引用的规范全名**未在池中声明**（`usr-`），或引用的 `engine-` 键不在 §三 总表内（**带参数尾缀的键族 `engine-item.*` / `engine-roll.npc.*` / `engine-roll.mod.*` 除外**，它们按 §三 总表的**族前缀**判定） | 该行标红＋"补一条声明"快捷操作；**导出不剔除该字段**；运行时该条判定不成立、该条修改不执行 |
| `K21` | `## Pool` 的 `pool` 段内**重复的 `name`** | 重复项标红；取先出现的一条 |
| `K22` | 写算子为 `divide` 且**值为 `0`** | 该行标红；运行时不执行 |
| `K23` | 写算子落在**只读的 `engine-` 键**上（§3.5 四类可写之外） | 该行标红；运行时不执行 |
| `K24` | 声明项的 `value` **与 `type` 不符** | 该行标红；按 `type` 取零值 |
| `K25` | 判定集合为**空**（`when` / `if` 存在但无条件） | 标黄"这条判定没有任何条件"；视为成立 |
| `K26` | `pool` / `when` / `if` 里使用的算子**不适用于该键的声明类型**（如对 `boolean` 用 `greater`） | 该行标红；运行时不执行（判定不成立） |
| `K27` | 声明的短名**含 `-` 或为空** | 标红并提示改用下划线 / 补名 |
| `K28` | 回合判定的 `deps` 引用了**不存在的别名** | 该依赖标红；运行时**仅忽略该条依赖**，**本条判定照常执行** |
| `K29` | `checks` 内**别名重复** | 重复项标红；取先出现的一个作为被依赖目标 |
| `K30` | 回合判定的依赖**成环** | **标红并给出环路路径**；**禁止保存 / 导出该依赖**（手写文件按声明顺序兜底） |
| `K31` | `deps` 指向一条**没有别名**的判定 | 该依赖标红（与 `K28` 同因）；运行时**仅忽略该条依赖**，**本条判定照常执行** |
| `K32` | `engine-item.<道具 id>` 的**道具 id 不在组件库** | 标黄提示"该道具不存在"；运行时按件数正常读写（不阻塞） |
| `K33` | 对话**同一层混用 `if` 与 `dice` / `hit`** | 标黄提示同层二选一；运行时**以 `if` 优先** |
| `K34` | if-else 链里**"无 `if` 记录"不在本层末尾**（其后的 `if` 永远不会被求值） | 标黄提示"该分支之后的条件不会生效" |
| `K35` | 使用处引用的**判定模板名未声明**（§4.5） | 该处标红；运行时该条件**恒不成立**（编辑器提供"补一条模板"快捷操作） |
| `K36` | **判定模板名与变量短名重名**（§6.1） | 重名处标红；取**先出现**的一条 |
| `K37` | 条件项**同时写了 `value` 与 `ref`**（§4.2），或 `ref` 与 `name` 的**类型不一致** | 标红；运行时**只认 `ref`** 并提示 |
| `K38` | 建筑实例的**槽位数 > `w × h`**（**V2.4**，[`02-data-model.md`](02-data-model.md) §4.9.3） | 该实例标红；运行时**只取前 `w × h` 个槽**（多余槽不抽定、不显示） |
| `K39` | 槽位的 `at` **越出建筑范围**（`dx ≥ w` 或 `dy ≥ h`，或为负） | 该槽标红；运行时该槽**落回缺省格**（字典序第 N 格） |
| `K40` | 同一实例**两个槽位的 `at` 相同**（NPC 互相重叠；**V2.4**） | 后声明的那一槽标红；运行时**保留先声明者**，后者落回缺省格 |

- 上述条目**一并纳入「清单」按钮**的汇总视图（§5.7）。
- **`K30` 是唯一一条"阻塞"校验**（其余只提示）。

## 十一、与既有裁决的关系

| 既有条目 | 关系 |
|---|---|
| 裁决 26 ⑧「对话**不记剧情旗标、不影响通关条件**」 | **继续有效、不作废**。状态池表达的是**由状态引起的反馈变化**：同一处内容在状态不同时给出不同的分支与代价（例：先前在别处取走了某位商人的货物，此后这位商人的报价条目改走"涨价"分支——"涨价"本身是该商人**预设的反馈分支**，不是引擎为剧情记的旗标）。池**不判定通关、不产生结局**。 |
